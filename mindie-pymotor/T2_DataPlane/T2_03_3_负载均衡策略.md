# 负载均衡策略

## 设计目标

LoadBalancePolicy 的设计目标是**将请求优先调度到当前负载最低的实例**，从而实现各实例间的负载均衡，避免出现部分实例过载而其他实例空闲的不均衡状态。

在 PD 分离架构下，负载均衡需要分别对 Prefill 实例池和 Decode 实例池独立进行，因为两者的负载衡量标准不同：Prefill 实例的负载取决于当前正在处理的请求数和已累积的 KV-Cache 大小；Decode 实例的负载则取决于显存占用和正在处理的序列数。

## 策略实现

LoadBalancePolicy 定义于 `motor/coordinator/scheduler/policy/load_balance.py`。核心类是 `LoadBalancePolicy`（第 36 行），继承自 `BaseSchedulingPolicy`。每个实例的得分由其当前 workload 和 endpoint 数量共同决定：

```python
# motor/coordinator/scheduler/policy/load_balance.py:L27-34
@dataclass(frozen=True)
class EndpointCandidate:
    instance: Instance
    endpoint: Endpoint
    score: float
```

`score` 的计算综合了实例级别的工作负载和 endpoint 级别的负载，权重由 `DEFAULT_ENDPOINT_INSTANCE_SCORE_WEIGHT = 0.05` 控制（第 24 行）。负载越低，得分越高，越容易被选中。

```python
# motor/coordinator/scheduler/policy/load_balance.py:L43-48
class LoadBalancePolicy(BaseSchedulingPolicy):
    def __init__(self, instance_provider: InstanceProvider):
        super().__init__(instance_provider=instance_provider)
        self._instance_provider = instance_provider
        self._endpoint_instance_score_weight = DEFAULT_ENDPOINT_INSTANCE_SCORE_WEIGHT
        logger.info("LoadBalancePolicy started.")
```

值得注意的是第 47 行的注释：`# Removed req_workload_dict - workload state is now managed by API Server's RequestManager`。负载状态的管理已经从 Scheduler 剥离到 RequestManager 中，Scheduler 只负责读取和选择，不再维护自己的负载副本。

## 得分计算逻辑

负载得分的核心公式大致为：

```
instance_score = endpoint_instance_score_weight × 当前 endpoint 负载 + 实例级别负载
```

`EndpointCandidate` 包含 instance、endpoint 和 score 三个字段，最终调度选择得分最高的 candidate。

## 配置参数

LoadBalancePolicy 本身不直接接收配置参数，其行为由 `CoordinatorConfig` 中的全局调度配置控制。关键配置项包括 `scheduling_policy` 字段，用于指定使用 LoadBalancePolicy 作为调度策略。

## 适用场景

负载均衡策略适合以下场景：

- **多实例并行处理**：当存在多个功能相同的 Prefill 或 Decode 实例时，均衡负载可以最大化整体吞吐率。
- **请求负载差异大的场景**：不同请求的计算量差异较大（如 prompt 长度差异大），使用负载均衡可以自动将大请求路由到当前负载较低的实例。
- **KVCache 复用不明显的场景**：请求之间前缀重复率低，亲和性调度的收益有限，此时负载均衡是更合理的默认选择。

## 与其他策略的关系

LoadBalancePolicy 与 KvCacheAffinityPolicy（详见 T2_03_2）的选择逻辑有一个重要区别：亲和性策略优先保证 KV-Cache 复用（可能选择负载较高的 Prefill 实例），而负载均衡策略优先保证实例间负载均匀（可能放弃 KV-Cache 复用的机会）。

在实际生产中，如果业务特征是长 prompt、多轮对话，建议优先选择 KVCacheAffinityPolicy；如果以短文本、随机请求为主，LoadBalancePolicy 是更稳定的选择。

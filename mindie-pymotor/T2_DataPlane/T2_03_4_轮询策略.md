# 轮询策略

## 设计目标

RoundRobinPolicy 是三种调度策略中**实现最简单**的一种：按顺序逐一选择实例，不考虑负载、不考虑 KV-Cache 亲和性，以轮询的方式将请求分配给各个实例。

轮询策略的设计目标不是最优调度，而是**可预测性和公平性**。在调试、压测和资源审计场景中，轮询策略的调度结果完全可重现，每次请求必然落到轮询序列的下一个实例，不存在随机性带来的干扰。

## 策略实现

RoundRobinPolicy 定义于 `motor/coordinator/scheduler/policy/round_robin.py`。其核心是两组计数器：

- `_instance_rr_counters: dict[PDRole | None, int]`：按角色维护实例级别的轮询计数器
- `_endpoint_rr_counters: dict[int | str, int]`：按 endpoint 维护 endpoint 级别的轮询计数器

```python
# motor/coordinator/scheduler/policy/round_robin.py:L30-37
class RoundRobinPolicy(BaseSchedulingPolicy):
    def __init__(self, instance_provider: InstanceProvider):
        super().__init__(instance_provider=instance_provider)
        self._instance_provider = instance_provider
        self._instance_rr_counters: dict[PDRole | None, int] = {}
        self._endpoint_rr_counters: dict[int | str, int] = {}
        self._instance_lock = Lock()
        self._endpoint_lock = Lock()
        logger.info("RoundRobinPolicy started.")
```

这两组计数器均使用 `threading.Lock` 保护，说明 RoundRobinPolicy 是**线程安全**的，可以在高并发环境下使用而不出现计数器竞争问题。

## 轮询选择逻辑

```python
# motor/coordinator/scheduler/policy/round_robin.py:L40-50
@staticmethod
def select_instance_from_list(instances: list[Instance], counter: int) -> tuple[Instance | None, int]:
    if not instances:
        return None, counter
    idx = counter % len(instances)
    return instances[idx], counter + 1
```

选择逻辑非常直接：用 `counter % len(instances)` 计算当前应选择的实例下标，返回该实例并递增计数器。计数器本身由调用方（Scheduler）维护，RoundRobinPolicy 自身不持有状态。

## 按角色独立轮询

轮询计数器以 `PDRole` 为 key 进行分组，这意味着 Prefill 实例池和 Decode 实例池拥有**独立的轮询序列**，互不干扰：

```python
# motor/coordinator/scheduler/policy/round_robin.py:L33
self._instance_rr_counters: dict[PDRole | None, int] = {}
```

Prefill 请求只在 Prefill 实例之间轮询，Decode 请求只在 Decode 实例之间轮询，与 PD 分离架构天然契合。

## 适用场景

RoundRobinPolicy 的典型适用场景包括：

- **调试和测试**：轮询结果完全可重现，便于定位问题。
- **负载均匀的固定-size 请求**：当所有请求规模相近、实例规格一致时，轮询等价于负载均衡。
- **资源审计和压测**：需要确保每个实例接收完全相同数量的请求时，轮询是最直接的手段。

## 局限性

轮询策略不考虑实例的实际负载，也不考虑 KV-Cache 复用。在以下场景中，轮询策略的表现会明显差于负载均衡或亲和性策略：

- 请求大小差异悬殊（大 prompt 和小 prompt 混排）
- 多轮对话场景（放弃 KV-Cache 复用将导致重复计算）
- 实例规格不一致（不同实例算力不同，轮询会导致小实例过载）

因此，RoundRobinPolicy 更适合作为调试工具而非生产默认策略。生产环境建议根据请求特征选择 KvCacheAffinityPolicy 或 LoadBalancePolicy（详见 T2_03_2 和 T2_03_3）。

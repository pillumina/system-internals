# T2_02_1_统一PD路由逻辑

`UnifiedPDRouter`（`motor/coordinator/router/strategies/unified_pd.py:63`）是 P/D 分离推理的主路径：当集群同时存在 prefilled 与 decode 实例且它们声明兼容的 dispatch capability 时，路由层将请求拆成 P/D 两条 leg 并发执行；引擎侧由 `DispatchAdapter`（详见 `T2_05_DispatchAdapter.md`）负责把 dispatch 协议收敛到具体的 vLLM/SGLang 调用格式。

## 入口与分支

`handle_request`（`unified_pd.py:135-145`）：

```python
async def handle_request(self) -> Response:
    await self.do_encode()                              # 1) 多模态 encode 预热
    self.is_meta = False
    if self.req_info.req_data.get("stream", False):
        self._stream_commit_controller = StreamCommitController.requiring({"prefill", "decode"})
        return CommitAwareStreamingResponse(
            self._generate_stream_response(),
            self._stream_commit_controller,
            on_first_body_sent=self._mark_stream_body_sent,
        )
    return await self._generate_response()
```

流式与非流式都先调用 `do_encode`（`base.py:612-669`）：当请求包含 `image_url` 或 `video_url` 的多模态消息且集群具备 `REQUIRED_MET_EPD` / `ENCODE_PREFILL` 就绪状态时，先向 encode 实例发送一次 `max_tokens=1, min_tokens=1, stream=false` 的预热调用，把图片/视频编码进 KV。

## 双 leg 生命周期：PDDispatchSession 与 AttemptContext

每个请求绑定一个 `PDDispatchSession`（`motor/coordinator/router/dispatch_session.py:184`），记录 `root_request_id` 与 `_attempt_seq` 计数器。每次重试生成一个新的 `AttemptContext`（`dispatch_session.py:47`），包含 `prefill_resource`、`decode_resource`、`pair_id`、`state`、`release_flags` 等字段。

`_create_attempt`（`unified_pd.py:302-323`）按以下顺序分配资源：

1. `await self._prepare_attempt_resource(PDRole.ROLE_P, attempt_seq)`：调 `_scheduler.select_and_allocate(ROLE_P, ...)`，状态变 `P_SCHEDULING → P_ALLOCATED`，并通过 `_record_attempt_workload` 在 `RequestManager` 写 `(req_id, attempt_seq, ROLE_P)` 的 workload 记录；
2. 若 P 分配成功，再调 D 分配；若 D 分配失败，**回滚 P** 的 `RELEASE_TOKENS` 与 `RELEASE_KV`，抛错让重试决策介入；
3. `session.new_attempt(p_resource, d_resource, self.config)` 返回带 `pair_id` 与 `attempt_seq` 的 `AttemptContext`。

`PDDispatchSession` 把 attempt 的 workload key 升级为 `(req_id, attempt_seq, role)` 元组，老 attempt 的延迟清理不会误释放新 attempt 的预占——这是 `motor/coordinator/domain/request_manager.py:107-110` 在 `add_req_attempt_workload` 里约定的语义。

## Dispatch 计划：handoff vs concurrent

`_select_dispatch_plan`（`unified_pd.py:709-713`）调用 `select_dispatch_plan_for_pair`：

- `DispatchPlan.PREFILL_HANDOFF_DECODE`：P 端先完成 prefill，返回 `PrefillResult`（含 `kv_transfer_params`），D 端再拿着 KV bootstrap 字段跑 decode。vLLM 的 `MOONCAKE_HANDOFF` / `CPCD_HANDOFF` 走这条路。
- `DispatchPlan.CONCURRENT_DECODE`（隐含分支）：P/D 同时跑，P 跑 prefill 写 KV，D 拿到 prompt 后用 `metaserver` URL 让 P 直接 push KV。

`_run_*_attempt`（`unified_pd.py:325-365`）按 dispatch plan 派发到 `_run_concurrent_stream_attempt` 或 `_run_handoff_stream_attempt`，两者都在 decode 阶段用 `StreamCommitController.mark_ready("decode", attempt_seq)` 标记 decode 就绪，handoff 路径额外用 `mark_ready("prefill", attempt_seq)`（`unified_pd.py:687-691`）。

## Prefill 任务并发与就绪位

`_run_concurrent_stream_attempt`（`unified_pd.py:337-368`）的关键设计：

```python
async with (
    self._client_for(attempt.prefill_resource) as p_client,
    self._client_for(attempt.decode_resource) as d_client,
):
    async def prefill_task():
        response = await self.forward_request(p_api, p_req, p_client, first_token_timeout)
        self._record_prefill_complete(response.json())
        self._stream_commit_controller.mark_ready("prefill", attempt.attempt_seq)

    p_task = attempt.register_prefill_task(asyncio.create_task(prefill_task()))
    async with aclosing(
        self._run_stream_decode_phase(attempt, d_client, d_api, d_req,
            stream_adapter_state, sampling_state=sampling_state, prefill_task=p_task)
    ) as decode_stream:
        async for chunk in decode_stream:
            yield chunk
```

decode 流循环内部用 `asyncio.Queue(maxsize=1)` + `terminal: Future`（`unified_pd.py:381-433`）实现非阻塞解码块分发，原子判断 `queue.get_nowait()`（`unified_pd.py:452-454`）避免 `empty()` 与 `get()` 之间的窗口。`_iter_stream_decode_queue` 在拿到每个 chunk 前都会先 `await prefill_task`，确保 prefill 失败立即传播到 decode，取消 decode leg。

## 请求构造：dispatch envelope 与 prefill result

`_request_for_attempt`（`unified_pd.py:652-679`）对每个 leg 构造请求 body：

1. 拷贝 `req_info.req_data`，将 `request_id` 改为 `{root_request_id}#a{attempt_seq}` 让引擎侧能区分 attempt；
2. `role == ROLE_P` 时设置 `stream=False` 且 `_apply_prefill_params` 把 `max_tokens=1`、去掉 `stream_options`；
3. 当 `reschedule_enabled` 时开启 `return_token_ids=True`；若有 retry plan，则应用 `Rescheduler.apply_retry_plan` 把 `prompt` 改为已生成 token 拼接剩余 prefix；
4. 当 `role == ROLE_D` 且 `precision_check_enabled` 时注入 `logprobs`（`inject_logprobs`，`unified_pd.py:670-675`）；
5. 将 `MotorDispatch` envelope 通过 `MOTOR_DISPATCH_KEY` 写入 body，让引擎侧 `DispatchAdapter.adapt_request_body` 解析；
6. 若 `_request_prefill_result` 返回了 `PrefillResult`，再写入 `MOTOR_PREFILL_RESULT_KEY`。

`PrefillResult` 必须满足 `_validate_prefill_result`（`unified_pd.py:693-707`）的 `root_request_id`/`pair_id`/`attempt_seq` 三元组一致性，否则视为错配抛错。

## 重试与回滚

流式重试入口在 `_generate_stream_response`（`unified_pd.py:155-209`）：

- 每个 attempt 开始前 `self._stream_commit_controller.begin_attempt(attempt.attempt_seq)`；
- 失败时 `_process_response_error`（`unified_pd.py:245-292`）分类取消原因（`NODE_FAULT`、`CLIENT_DISCONNECT`、其他），决定是否进入下一次 attempt；
- 节点故障类取消默认可重试（只要 `_stream_retry_allowed` 允许），客户端断连或调度 abort 不可重试；
- `_release_attempt`（`unified_pd.py:741-784`）按 `AttemptReleaseFlags` 严格幂等释放：prefill 的 `RELEASE_TOKENS` → `RELEASE_KV`、decode 的 `RELEASE_TOKENS`，避免重复扣减 workload。

非流式 `_generate_response`（`unified_pd.py:210-243`）结构相同但没有 commit barrier。

## 精度采样与日志

当 `token_sampling_config.precision_check_enabled=True` 时：

- `_collect_logprobs_from_stream_chunk`（`unified_pd.py:851-867`）从每个 SSE chunk 中抓 `logprobs`，累加到 `sampling_state["info"]`，随后调用 `strip_logprobs_for_client` 把日志中的 logprobs 抹掉；
- `_maybe_submit_sample`（`unified_pd.py:885-901`）在 decode 完成时通过 `SamplingManager.confirm_sample` 决定是否本帧上报；上报时调用 `_submit_token_sample` 把 `(prefill_id, decode_id, info)` 提交给 scheduler。

`handle_metaserver_request`（`unified_pd.py:907-943`）是 CDP 模式下 D 侧把 prefill 回投到 P 实例的入口：单独选一个 `ROLE_P` 资源、把 `stream=False` 后转发，结果中提取 `usage` 与 `prompt_tokens_details`。

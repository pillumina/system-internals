# T1_03 整体架构

MindIE PyMotor 是一个五组件的分布式推理服务平台。本节从顶层视角给出每个组件的职责边界与典型交互路径，便于读者在阅读后续章节时建立「这段代码属于哪个组件、与谁通信」的索引。整体架构描述见 `docs/zh/architecture.md`。

## 五大组件概览

| 组件 | 角色 | 关键进程入口 |
|------|------|--------------|
| Coordinator | 集群数据面入口，负责接收推理请求并完成 P/D 路由 | `motor/coordinator/main.py` |
| Controller | 集群控制面大脑，负责实例身份、故障与 RAS 决策 | `motor/controller/main.py` |
| EngineServer | 节点级推理服务进程，对外暴露 OpenAI 兼容接口 | 由 NodeManager 拉起 |
| NodeManager | 节点级进程与生命周期管理者，负责注册、心跳、引擎拉起 | `motor/node_manager/main.py` |
| Deployer | K8s 部署参考脚本与运维工具集 | `examples/deployer/` |

下文按「数据面 vs 控制面」分组说明每个组件的边界，最后用一条典型请求链路把组件串起来。

## Coordinator：数据面入口

Coordinator 是用户请求的统一入口，包含：

- **Endpoint 层**：业务面 OpenAI 兼容接口（chat/completions 等），以及管理面 `/health`、`/metrics` 等探针接口——见 `motor/coordinator/api/` 与 `motor/coordinator/main.py`。
- **Router 层**：根据可用实例角色与 Connector capability 选择 `UnifiedPDRouter` 或 `PDHybridRouter`，分发到具体的 P/D 实例——见 `motor/coordinator/router/dispatch.py` 与 `T2_03_Scheduler调度器`。
- **Scheduler**：负载均衡调度器，根据策略（`load_balance` / `round_robin` / `kv_cache_affinity`）选择实例与 endpoint，并维护 workload ledger——见 `motor/coordinator/scheduler/`。
- **RequestManager / InstanceManager**：请求级与实例级状态管理。

Scheduler 在跨进程部署时被拆为独立 Scheduler 进程，二者通过 ZMQ（`motor/coordinator/scheduler/runtime/zmq_protocol.py`）+ 共享内存（`workload_shm/`）通信——这是为了在多 worker 模式下让所有 worker 看到一致的 workload ledger，详见 `T8_02_SharedMemory布局` 与 `T8_03_ZMQ协议设计`。

## Controller：控制面大脑

Controller 不参与请求转发，专注于集群级决策：

- **FaultManager**：单例观察者，订阅 `ResourceMonitor` 的 K8s ConfigMap/Node 状态变更，按故障等级决定隔离/恢复，并触发对应恢复策略——见 `docs/zh/design/fault_tolerance/overview.md` 与 `T4_01_FaultManager设计`。
- **InstanceAssembler**：把多个 NodeManager 注册的 endpoint 组装成 `Instance`，等到所有 NodeManager 上线后才下发 StartCmd——这是 K8s Pod 重启后自动重拉起链路的核心，见 `T4_02_InstanceAssembler组装`。
- **InstanceManager**：实例生命周期管理（INITIAL → INACTIVE → ACTIVE → PAUSED → DELETED），与 FaultManager 通过 `forced_separated_instances` 集合协作。
- **策略中心**：把故障等级 + 故障码映射到具体恢复策略（L2 → `TokenReinferenceStrategy`，L4/L5/L6 + decode → `ScaleP2DStrategy`），见 `motor/controller/fault_tolerance/strategy/`。
- **EventPusher**：把实例状态变化推送给 Coordinator；**CCAEReporter**：可选上报给 CCAE 运维平台。

## EngineServer 与 NodeManager：节点级

EngineServer 是「实际算力提供者」，对外暴露 OpenAI 兼容 RESTful 接口，南向对接 vLLM-Ascend / SGLang / MindIE（当前版本仅支持 vLLM）。它不知道自己属于 Prefill 还是 Decode，只接受请求并完成推理；身份由 NodeManager 启动时收到的 `StartCmdMsg.role` 决定。

NodeManager 是节点级「监护人」，提供：

- **进程级注册**：`EngineManager._register()` 向 Controller 发送 RegisterMsg；Controller 重启后通过 `ReregisterMsg` 携带已有的 `instance_id` 与 endpoints 还原身份。
- **心跳上报**：`HeartbeatManager` 周期性上报；Controller 返回 503 时会触发 `_reregister()`。
- **引擎拉起**：`Daemon.pull_engine()` 在收到 `StartCmdMsg` 后启动 EngineServer 子进程。

NodeManager ↔ Controller 的协议在 `T8_03_ZMQ协议设计` 中有交叉说明；故障感知与拉起链路详见 `T4_02_InstanceAssembler组装`。

## Deployer：部署工具集

Deployer 不参与运行时，而是把上述组件部署到 K8s 上：

- **Deploy**（`examples/deployer/deploy.py`）：一键启动/停止服务，按 `motor_deploy_config` 渲染 Deployment。
- **Probe**：配置 K8s 健康探针（liveness/readiness/startup）。
- **LogCollector**：日志收集脚本。
- **BootHelper**：容器启动脚本，自动配置环境变量。

它通过 K8s Service 把 Coordinator 的推理端口暴露给客户端，是整个体系的「外部入口」。

## 一条典型请求的链路

把上面五组件串成一条请求链路：

```
Client → Deployer 暴露的 K8s Service → Coordinator.Endpoint
       → Router（UnifiedPDRouter 或 PDHybridRouter）
       → Scheduler（select_instance + allocate workload）
       → EngineServer（P 实例完成 Prefill → 通过 Connector 把 KV 送到 D 实例）
       → EngineServer（D 实例完成 Decode → 流式/非流式回包）
       → Coordinator 把响应回给 Client
```

如果中间任意一步失败：

- 引擎侧故障由 `BaseRouter._process_response_error`（`motor/coordinator/router/strategies/unified_pd.py:L245-L292`）按 retry/stop 语义处理。
- 节点级故障由 Controller 的 `FaultManager` 检测并按 `ScaleP2DStrategy` / `TokenReinferenceStrategy` 恢复，详见 `T4_03_FaultManager策略调度`。

# T1_04 技术定位

MindIE PyMotor 在推理栈中扮演「北向 API 兼容、南向进程管理、中段状态编排」的角色。本节给出它在整体推理栈中的位置、与上下游组件的边界，以及为什么这套定位契合生产级 LLM 服务的需求。整体架构与组件依赖关系见 `docs/zh/architecture.md`，组件详细职责见 `T1_03_整体架构`。

## 在推理栈中的位置

把 MindIE PyMotor 放进推理栈的纵切面，可以看到三层清晰的接口边界：

| 层 | 组件 | 对 PyMotor 的接口 |
|----|------|--------------------|
| 上：客户端 / 业务方 | OpenAI 兼容客户端、业务网关 | 通过 K8s Service 调用 Coordinator 的 OpenAI 兼容 RESTful 接口 |
| 中：MindIE PyMotor | Coordinator / Controller / NodeManager / EngineServer / Deployer | （PyMotor 本体） |
| 下：推理引擎 + 资源 | vLLM-Ascend / SGLang / MindIE，昇腾 NPU、HCCL、HBM | EngineServer 通过 OpenAI 兼容 HTTP 与 vLLM-Ascend 对接；NodeManager 通过 K8s + K8s ConfigMap 与集群基础设施交互 |

PyMotor 的「定位」是 **介于业务接入和推理引擎之间的中间层**：不直接做矩阵计算，但负责请求调度、集群状态与生命周期管理；不直接给业务方暴露 GPU，但负责把请求准确送达合适的算力节点。

## 北向：OpenAI API 兼容

Coordinator 对外暴露 OpenAI 兼容 RESTful 接口（`chat/completions`、`completions` 等），这一点从 `motor/coordinator/main.py` 与 `motor/coordinator/api/` 可以直接看到。这样做的实际意义：

- 业务方可以无缝接入：现有基于 OpenAI SDK 的客户端不需要修改就能把流量切到 PyMotor 后端。
- 多模型统一入口：业务方只关心模型名（如 `qwen3-8B`），由 PyMotor 决定请求落到哪个实例。
- 协议兼容层：Coordinator 内置了 `completion_to_chat`（`motor/coordinator/router/adapters/completion_to_chat.py`）等适配器，把 `text_completion` 形态自动转回 `chat_completion` 响应——这是 PyMotor 把 OpenAI 兼容性当成一等公民的具体体现。

业务面之外，Coordinator 还提供 `/health`、`/metrics`、`/readiness`、`/liveness` 等管理面接口供 K8s 探针与运维平台使用，见 `motor/config/coordinator.py:L74-L99` 中的 skip_paths 与 rate limit skip paths 定义。

## 中段：状态编排与调度

PyMotor 的核心是中段的「状态编排」：

- **Coordinator ↔ Controller**：通过 `EventPusher`（Controller 侧）同步实例状态与故障等级；Coordinator 接收事件并刷新本地的 InstanceManager 视图（`motor/coordinator/domain/instance_manager.py`）。
- **Coordinator ↔ EngineServer**：通过 HTTP 把请求转发到 EngineServer 的 OpenAI 兼容端口；通过 ZMQ + 共享内存把 workload 变更同步给 Scheduler 进程。
- **Controller ↔ NodeManager**：通过 RegisterMsg / StartCmdMsg / HeartbeatMsg 三类消息维持节点身份与生命周期。

这一层的关键设计原则是 **「协议收敛在 PyMotor 内部」**：业务方只需要和 Coordinator 对话，下层的 EngineServer 也不需要知道有 Coordinator 存在——它们只看 HTTP 请求。

## 南向：vLLM-Ascend / SGLang 适配

PyMotor 南向对接 vLLM-Ascend（当前主推）和 SGLang。这一适配的关键不在 HTTP 协议（EngineServer 暴露的也是 OpenAI 兼容接口），而在 Connector 的协同语义：

- NodeManager 启动 vLLM 时读取 `kv_transfer_config.kv_connector`，按 `docs/zh/design/pd_disaggregation.md` 中的识别白名单推导 `dispatch_capabilities`。
- 当 vLLM Connector 不在白名单内时，可在 `motor_engine_prefill_config` / `motor_engine_decode_config` 顶层用 `dispatch_profile` 显式声明 `handoff` 或 `trigger`，作为逃生口。
- 不识别的 Connector 会被判为 `unknown`，Coordinator 拒绝配对（503），避免运行时才发现不兼容。

这套机制把 PyMotor 与具体 Connector 的耦合点显式化——业务方不需要知道 Connector 是什么，但 PyMotor 必须知道 P/D 两侧的 Connector 能否协同。

## 节点级：NodeManager 接管进程管理

NodeManager 在节点侧承担两个角色：

- **进程管理**：拉起 EngineServer、监控子进程状态、在子进程异常退出时上报心跳超时——这与 `Controller.Observability` 上报的 `ServerExceptionReason.HEARTBEAT_TIMEOUT` 直接对应。
- **资源观测**：通过订阅 `kube-system` 命名空间下的 `mindx-dl-deviceinfo-{node_name}` ConfigMap，把 NPU 故障（`CardUnhealthy` / `CardNetworkUnhealthy`）和交换机故障转换为 `FaultInfo` 上报给 Controller。

也就是说，PyMotor 不直接调用 K8s API 完成扩缩容（那是 Controller 与 K8s CRD 的边界），而是通过 NodeManager 把「节点状态变化」显式地反应到集群状态机里，再由 Controller 决定是否隔离、是否触发恢复策略。

## 集群级：Controller 接管集群状态

Controller 的「集群状态」包括：

- 实例组装队列（`InstanceAssembler._instances_assembler_loop`）。
- 实例状态机（INITIAL → ACTIVE → PAUSED → INACTIVE → DELETED）。
- 强制隔离集合（`forced_separated_instances`）。
- 故障等级与策略映射（`strategy.py`）。

Controller 与 PyMotor 之外的世界通过两个渠道交互：

- **CCAEReporter**（可选）：把 Metrics 与状态变化推送给华为 CCAE 运维平台。
- **EventPusher**：把状态变化推回 Coordinator，使 Coordinator 的本地视图与 Controller 一致。

## 这套定位的工程含义

把上述四层边界放在一起，PyMotor 的定位可以总结为：

- **业务方**：只看到 OpenAI 兼容 HTTP 接口，模型维度寻址，对 P/D 拓扑无感。
- **运维方**：只通过 K8s、CCAE、日志与 PyMotor 交互，拓扑变化（Pod 启停、NPU 故障）由 Controller 自动收敛。
- **引擎方**：只暴露 OpenAI 兼容 HTTP 接口，对 Coordinator / Controller 无感，按 `StartCmdMsg.role` 决定自己的身份即可。

这套「把复杂性收敛在中间层」的设计，是 PyMotor 能在生产环境中支撑高可用、可运维、可演进 LLM 服务的基础。后续 `T1_05_关键概念一览` 会进一步给出贯穿全栈的关键概念定义。

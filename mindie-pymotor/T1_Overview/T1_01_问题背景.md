# T1_01 问题背景：为什么需要 PD 分离

LLM 在线推理的两阶段——Prefill 与 Decode——在硬件资源的需求结构上截然不同，把它们揉在同一实例上跑会出现典型的「短板效应」（barrel effect）。本节从这两阶段的算力特征出发，解释混合部署的资源浪费，并交代后续 PD 分离设计的动机。

## Prefill 阶段的资源画像

Prefill 是对整段 prompt 的一次性前向计算：模型需要同时处理 prompt 内所有 token，构造完整的注意力矩阵并写入 KV Cache。这一步的算力主要落在矩阵乘和张量收缩上，是**计算密集型**（compute-bound）——NPU 的算力上限（FLOPs）是最先被吃满的维度，显存带宽压力反而次要。由于 KV Cache 是一次性生成、之后可被多个 Decode 请求复用，集群层面也存在明显的「跨请求共享」潜力。

## Decode 阶段的资源画像

Decode 阶段每一步只生成一个 token，自回归地推进。每次前向只读取上一时刻的 KV Cache、对当前最新 token 做 attention 与采样，矩阵规模极小，但访存模式是「高频小数据」——每个 token 都要把整段历史 KV 从 HBM 搬运到计算单元。因此 Decode 是**访存密集型**（memory-bandwidth-bound）——瓶颈在 HBM 带宽与 KV Cache 的有效驻留，与 Prefill 的瓶颈维度正交。

## 混合部署的短板效应

如果把 Prefill 与 Decode 放在同一实例、同一 NPU 上分时复用，二者会互相干扰：

- **Prefill 抢占算力**：Prefill 一旦在某个 batch 中触发，整卡的算力被吃满，Decode 的 token 生成必须等待 Prefill 算完才能继续推进，TTFT 与 TPOT 同时恶化。
- **Decode 抢占带宽**：Decode 在持续搬运 KV 时，Prefill 的写 KV 与 Prefill 的矩阵乘都要和它抢带宽，导致 Prefill 的算力利用率反而上不去。
- **KV Cache 碎片化**：混合部署下，单实例必须同时保留 Prefill 中间态与 Decode 上下文，显存规划互相牵制，留给任一阶段的容量都被压缩。

最终结果就是「两阶段都跑不满」：实例的整体吞吐由二者中较慢的那个决定——这是典型的短板效应。

## 从源码看两种角色的资源分离

Motor 在代码层面的角色抽象体现在 `PDRole` 枚举（`motor/common/resources/instance.py:L41-55`）：

```python
class PDRole(str, Enum):
    ROLE_E = "encode"
    ROLE_P = "prefill"
    ROLE_D = "decode"
    ROLE_U = "union"
```

`Instance.role` 字段（`motor/common/resources/instance.py:L151`）在 Controller 组装实例时被填入，决定了该实例在调度时被归入哪个角色池（`motor/coordinator/domain/scheduling.py:L56-89` 的 `readiness_from_instances`）。

Decode 实例的负载衡量维度是 `active_kv_cache`（当前 KV Cache 显存占用）和 `active_tokens`（当前在处理的 token 数），由 `Workload` 数据类（`motor/common/resources/endpoint.py:L22`）承载。相比之下，Prefill 实例的负载只取决于 `active_tokens`（因为 Prefill 阶段的 KV Cache 是写入侧，尚未累积到被 Decode 共用的体量）。这两种负载衡量指标的差异，正是 PD 分离后各自调度的基础。

## 短板效应的量化表现

Prefill 与 Decode 在资源竞争上的量化差异，可以用各自的瓶颈维度来理解：

- **Prefill 瓶颈**：单次前向的 FLOPs 与模型参数规模成正比（70B 模型做一次 Prefill 需要约 140 TFLOPs），GPU/NPU 的张量计算单元利用率是首要指标。
- **Decode 瓶颈**：每次只做一个 token 的 attention，但 KV Cache 体量随序列长度线性增长——一个 4096 上下文的请求，其 KV Cache 可能是 128 上下文请求的 32 倍，HBM 带宽是首要瓶颈。

这两类指标在硬件上往往是此消彼长的关系：Prefill 打满算力时 GPU 时钟频率会升高，Decode 持续搬运 KV 时显存带宽争用。这直接导致"两阶段都在跑但都跑不到峰值"的局面。

## 解法：把两阶段放到不同实例上

把 Prefill 放到专用 Prefill 实例、把 Decode 放到专用 Decode 实例，让各自的硬件资源画像与工作负载对齐：

- Prefill 实例可以专心吃满算力（设置大 batch、更激进的并行策略），不再被 Decode 的高频小数据打断。
- Decode 实例可以专注于 KV 驻留与带宽利用，批量调度多个请求的 token 步，进一步压低单 token 成本。
- 二者之间通过 KV 传输（KV transfer）衔接，把 Prefill 生成的 KV Cache 送到 Decode 端复用——这正是调度层需要感知 PDRole 的根本原因。

如此一来，「短板」变成了「两块板各管各的」，集群整体吞吐受限于二者中较慢的那一项，但二者可以各自跑到接近硬件上限，从而显著降低短板效应的损失。

# T4_03_2 P2D 扩容触发条件

## 总览

P2D（Scale Prefill to Decode）扩容不是无条件触发的自动恢复，而是一组**严格收敛**的条件组合：故障等级、实例角色、配置开关、集群容量、隔离状态必须同时满足才进入执行。任一条件不满足，FaultManager 要么保持现有策略不变，要么降级为单纯隔离、不启动 P2D。本节梳理完整的触发判定链路。

## 触发链路

```text
ResourceMonitor 推送 ConfigMap/Node 故障
        │
        ▼
FaultManager._refresh_instance_fault_level
  ├── PreSeparateNPU 动态重评
  ├── 聚合 instance 故障等级
  └── InstanceManager.separate_instance (>L2) / recover_instance (≤L2)
        │
        ▼
FaultManager._process_instance_strategy
        │
        ▼
策略路由：fault_level → strategies[fault_level]()
        │
        ▼
level4_strategy / level5_strategy / level6_strategy
        │
        ▼
判定：enable_scale_p2d && role == "decode" && 返回 ScaleP2DStrategy
        │
        ▼
线程池提交 ScaleP2DStrategy.execute
```

## 判定要素

### 1. 故障等级

仅 L4、L5、L6 三个等级可触发（`motor/controller/fault_tolerance/strategy/strategy.py:71-93`）。映射关系：

| FaultLevel | OriginFaultLevel | 策略工厂 |
|------------|------------------|----------|
| L1, L2, L3 | `NotHandleFault`、`RestartRequest`、`RestartBusiness` | 不返回 `ScaleP2DStrategy` |
| L4 | `FreeRestartNPU` | `level4_strategy` → `ScaleP2DStrategy`（仅 decode） |
| L5 | `RestartNPU` | `level5_strategy` 委托 L4 |
| L6 | `SeparateNPU`、`PreSeparateNPU` | `level6_strategy` 委托 L4 |

L3 故障当前没有专属恢复策略：仅执行 `separate_instance`，由运维或 K8s 重启 Pod 触发后续自动重注册流程（详见 `docs/zh/design/fault_tolerance/overview.md` 的 §2 自动重拉起注册）。

### 2. 实例角色

`level4_strategy` 在 `strategy.py:79-83` 中显式判断：

```python
instance = InstanceManager().get_instance(instance_id)
if instance is not None and instance.role == "decode":
    return ScaleP2DStrategy
else:
    return None
```

该检查决定了 P2D 的**单向性**：只有 Decode 实例故障时才"借用" Prefill 的节点资源；Prefill 实例 L4+ 故障不会触发 P2D（也避免反向占用造成 P 池耗尽）。

### 3. 配置开关

`level4_strategy` 首行检查 `config.fault_tolerance_config.enable_scale_p2d`（`strategy.py:73`）。关闭时直接返回 `None`，故障仅触发隔离但不执行 P2D。该开关允许运维在容量敏感场景下临时关闭 P2D 行为。

### 4. 隔离门

策略被调度后，`ScaleP2DStrategy._check_d_instance_status`（`scale_p2d.py:314-433`）强制等待 D 实例状态进入非 `INITIAL/ACTIVE` 状态：

- D 实例 `INITIAL/ACTIVE`：视为故障自愈，ScaleP2D 提前返回（`not_needed` 路径）。
- D 实例 `INACTIVE/DELETED`：可执行抢占。
- 等待超过 `scale_p2d_d_instance_reinit_wait_timeout` 秒仍处于活跃状态：策略失败。

该门确保只有在 D 已经被 `InstanceManager.separate_instance` 隔离、不再承接业务流量时才允许 stop P 实例。

### 5. 容量校验

`_select_p_instances_to_kill`（`scale_p2d.py:435-534`）计算：

```
num_available_node = num_node_per_instance_P × (operational_p_count - 1)
required_nodes    = num_required_node = D 实例 L3+ 故障节点数
```

`num_available_node < required_nodes` 时拒绝执行：

- 预留 1 个 Prefill 实例避免 P 池完全清空。
- 不计入 `INACTIVE/DELETED` 的 P 实例，确保 `stop` 接口可被 NodeManager 处理。

### 6. 故障节点统计

`_get_faulty_node_count`（`scale_p2d.py:265-312`）调用 `FaultManager.get_node_fault_levels(d_instance.id)`（`fault_manager.py:251-280`）获取该实例下每个节点的最高故障等级，统计 `>= L3` 的节点数：

- 当 FaultManager 未跟踪到任何节点元数据时，保守视为全部节点故障（`return len(node_managers)`），倾向过度抢占以保证恢复。
- 元数据完整时，仅统计真正 L3+ 的节点。

## 触发决策示意

| 等级 | 角色 | enable_scale_p2d | D 已隔离 | 容量足够 | 结果 |
|------|------|------------------|----------|----------|------|
| L4 | decode | true | 是 | 是 | 启动 ScaleP2D |
| L4 | prefill | true | — | — | 不启动 |
| L4 | decode | false | — | — | 仅隔离 |
| L6 | decode | true | 否（仍 ACTIVE） | — | 等待超时，FAILED |
| L4 | decode | true | 是 | 否 | 容量不足，FAILED |

## 不触发的典型场景

1. **软件故障**：所有 `EngineStatusType` 故障（`DEAD=1`、`UNHEALTHY=2`）映射到 `L2`，由 `level2_strategy` 处理或仅做等级上报（`strategy.py:51-63`），不进入 ScaleP2D 路径。
2. **L1 子健康故障**：`NotHandleFault`/`SubHealthFault` 映射到 `L1`，策略工厂返回 `None`，无动作。
3. **缩 P 保 D 已经发起但尚未完成**：FaultManager 在 `_process_instance_strategy` 中通过 `strategy_fault_level` 记录当前策略级别，避免同级别抖动（`fault_manager.py:540-552`）。

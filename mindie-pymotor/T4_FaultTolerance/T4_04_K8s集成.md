# T4_04 K8s 集成

## 概述

FaultManager 通过 Kubernetes API 监听两类资源：

- **Node**：用于捕获节点级 Ready/NotReady 变化，作为 `NODE_REBOOT` 故障的来源（fault_code `0x0000001`，等级 L6）。
- **ConfigMap**：用于接收驱动/固件上报的设备与交换机故障（`DeviceInfoCfg` / `SwitchInfoCfg`），并解析为 `FaultInfo`。

实现分布在三个文件：

- `motor/controller/fault_tolerance/k8s/k8s_client.py`：通用 K8s 客户端（Pod IP → NodeName 反查）。
- `motor/controller/fault_tolerance/k8s/resource_monitor.py`：每节点一个的 Watch 守护器。
- `motor/controller/fault_tolerance/k8s/configmap_parser.py`：ConfigMap 数据反序列化与字段规范化。

## K8sClient

`K8sClient`（`k8s_client.py:18-57`）是轻量级封装。`__init__` 优先尝试 `config.load_incluster_config()`（Pod 内），失败回退到 `config.load_kube_config()`（开发环境）。当前唯一对外方法是 `get_node_hostname_by_pod_ip(pod_ip)`：通过 `list_pod_for_all_namespaces(field_selector=f"status.podIP={pod_ip}")` 反查 Pod 所在 Node。该方法供 FaultManager 在软件故障上报时将 `pod_ip` 关联到 `NodeMetadata.node_name`（`fault_manager.py:282-330`）。

## ResourceMonitor

`ResourceMonitor`（`resource_monitor.py:30-487`）是每个 K8s Node 一份的复合监听器，内部启动两个守护线程：

| 线程 | 监听对象 | 字段选择器 |
|------|----------|------------|
| `_monitor_node` | `list_node` | `metadata.name={node_name}` |
| `_monitor_configmap` | `list_namespaced_config_map` | `metadata.name={configmap_name_prefix}{node_name}` |

### Watch 与重连策略

两个监听线程使用 `kubernetes.watch.Watch` 流式接收事件（`resource_monitor.py:200-224, 281-308`）。为应对 K8s API 中断、Watch 超时（`410 Gone`）等异常，实现了**指数退避**：

- 默认初始退避 1s，最大 60s（`_BACKOFF_INITIAL`、`_BACKOFF_MAX`，`resource_monitor.py:41-42`）。
- `410` 资源版本过期时使用更短的退避（`_BACKOFF_410 = 2s`，`resource_monitor.py:44`），避免长时间阻塞。
- 连续失败时 `consecutive_failures` 累加，每次重连后由成功事件重置为 0。

监听线程的初始化阶段会做一次 `list_*` 调用获取当前 `resource_version`，并立即以 `ADDED` 事件处理初始状态，避免错过 Watch 启动前的最新数据（`resource_monitor.py:180-190, 252-266`）。

### 变更去重

`_handle_node_change` 通过 `last_node_status` 缓存避免对同一 `NodeStatus` 重复触发回调（`resource_monitor.py:348-381`）；`_handle_configmap_change` 用 `_has_fault_info_changed`（`resource_monitor.py:422-450`）按 `fault_code` 去重，仅在等级或类型真正变化时调用回调，避免 ConfigMap 中只有时间戳变化时无谓触发故障重评。

### 节点变更回调

回调签名 `node_change_handler(NodeStatus, node_name)` 由 FaultManager 在 `_create_resource_monitor_for_node` 中注入：节点进入 `NOT_READY` 时注入 `NODE_REBOOT` 故障，恢复 `READY` 时清除该故障码（详见 `docs/zh/design/fault_tolerance/overview.md` §1.1）。

### ConfigMap 变更回调

回调签名 `configmap_change_handler(list[FaultInfo], node_name)` 处理解析后的故障列表。`ConfigMap` 删除事件以**空列表**形式回调，表示该节点当前没有已知故障。

## ConfigMap 解析

`configmap_parser.py` 处理 MindCluster 上报的 ConfigMap 数据。ConfigMap 至少包含以下字段之一才会被识别为有效：

- `DeviceInfoCfg`：NPU 设备故障（`CardUnhealthy`、`CardNetworkUnhealthy`）。
- `SwitchInfoCfg`：交换机端口故障。
- `ManuallySeparateNPU`：手动隔离指令（仅日志记录，不直接产生故障，参见 `configmap_parser.py:473-479`）。

`is_configmap_valid`（`configmap_parser.py:43-53`）通过三者交集判断格式。

### DeviceInfoCfg 解析

`process_device_info`（`configmap_parser.py:184-226`）支持新旧两种字段名：

- 新：`huawei.com/npu-Fault`、`huawei.com/npu-NetworkUnhealthy`
- 旧：`huawei.com/Ascend910-Fault`、`huawei.com/Ascend910-NetworkUnhealthy`

`_resolve_device_list_key`（`configmap_parser.py:166-181`）按顺序尝试新/旧键，确保跨 MindCluster 26.0.0 升级时的兼容性。DeviceList 字段支持两种序列化形式：原生 JSON 数组，或字符串包裹的 JSON 数组（`_normalize_device_list_value`，`configmap_parser.py:150-163`）。

故障码字段可能为逗号分隔的多个十六进制数（`_parse_device_fault_code`，`configmap_parser.py:56-74`），取第一个可解析的码作为 `fault_code`，默认 `0x1001`。

### SwitchInfoCfg 解析

`process_switch_info`（`configmap_parser.py:318-349`）解析交换机级故障，支持两种 fault_key 格式：

- 新格式（MindCluster 26.0.0+）：`0x2001_1_2`
- 旧格式：`[0x2001,info]_1_2`

`_parse_switch_fault_key`（`configmap_parser.py:229-267`）按 `_` 切分并尝试两种前缀格式，最终回落到默认 `0x2001`。

`_normalize_fault_level_string`（`configmap_parser.py:77-103`）将 MindCluster 26.0.0+ 简写的 `NotHandle`、`Separate` 转换为标准 `OriginFaultLevel` 字符串。

## 与 FaultManager 的协作

`_create_resource_monitor_for_node`（位于 `_ResourceManagerMixin`）在每个 NodeMetadata 加入时启动一个 ResourceMonitor，监听器回调直接调用 `FaultManager._handle_fault_info_update`（详见 `docs/zh/design/fault_tolerance/overview.md` §1.1 与 T4_02_FaultManager.md）。

配置热更新时（`configmap_prefix` / `configmap_namespace` 变化），所有 ResourceMonitor 被停止并以新配置重建（`fault_manager.py:185-201`）。

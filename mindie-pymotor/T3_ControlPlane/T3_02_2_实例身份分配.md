# T3_02_2_实例身份分配

PD 实例在 Controller 中由 `PDRole` 标识身份，调度时按 role 选实例（`Scheduler.get_available_instances(role)`），不同 role 的实例天然隔离。Controller 负责在实例注册、扩缩容、故障恢复三种场景下做"身份分配"——本文梳理身份体系、分配时机与动态调整机制。

## PDRole 身份体系

`PDRole`（`motor/common/resources/instance.py`）：

```python
class PDRole(str, Enum):
    ROLE_E = "encode"     # Encode，EPD 三阶段专用
    ROLE_P = "prefill"    # Prefill
    ROLE_D = "decode"     # Decode
    ROLE_U = "union"      # Prefill + Decode 一体（混合部署）
```

调度语义：

- `ROLE_P`/`ROLE_U` 是 prefill 合法目标，`KV_CACHE_AFFINITY` 策略仅对这两个 role 生效（详见 `T2_03_2_KVCache亲和性调度.md`）；
- `ROLE_D`/`ROLE_U` 是 decode 合法目标；
- `ROLE_E` 仅在 EPD 模式下被 E 阶段调度，`InstanceReadiness.REQUIRED_MET_EPD` 才视为就绪；
- `ROLE_U` 与 `ROLE_P` 都会被注册到 Conductor（`_KVA_ROLES = frozenset({PDRole.ROLE_P, PDRole.ROLE_U})`，`conductor_api_client.py:25`），`ROLE_D` 不上 Conductor。

## 初始身份分配

实例的初始身份在 `add_instance(ins)`（`instance_manager.py:353-388`）时被记录到 `Instance.role`。这一字段由调用方（典型是 `InstanceAssembler` 在节点启动时根据 deploy_config 决策）写入。Controller 不会在收到 `StartCmdMsg` 后**重新**决定 role——它只信任上游装配好的角色分配，避免控制面与数据面出现角色偏差。

`Instance.role` 一旦写入就跟随实例整个生命周期，状态机转移（ACTIVE/INACTIVE/PAUSED/DELETED）不会改变 role。

## 动态调整机制

`InstanceManager` **不直接提供**修改 `Instance.role` 的 API——这是有意的设计：role 是调度可见性的核心维度，运行时变更必须经过完整的事件链才能让 Coordinator 重新加载。动态调整的实际路径是：

### ScaleP2D 场景下的"减少 P"（不是改 role）

故障导致 D 实例不足时，ScaleP2D 恢复不会把 P 实例改成 D——D 的算力与显存特征与 P 不同，强行改造会影响 Prefill 性能。实际做法是 FaultManager 调 `InstanceManager.separate_instance(p_id)` 把若干 P 实例标记强分离并下线（详见 `T3_02_1_实例生命周期.md`），让剩余的 P/D 实例比重新达到平衡。

### 滚动更新下的"换实例"

当需要给已有 role 换新配置时，运维不会直接改 `Instance.role`，而是：

1. 触发滚动更新流程（部署侧 Deployer）；
2. 老实例由 NodeManager 收到 `PreStop` 信号 → 上报 `INSTANCE_PAUSED` 心跳 → `InstanceManager` 切到 PAUSED；
3. 新实例被装配成同 role 加入 `InstanceManager`，经历 INITIAL → ACTIVE 流程；
4. 老实例最终心跳超时走 DELETED。

### Conductor 重新注册

当 `Instance.role` 在某些场景下需要调整（比如新增 ROLE_E 支持），EventPusher 会重发 `EventType.SET` 让 Coordinator 完全重建 instance 视图（详见 `T3_03_EventPusher.md`）。Coordinator 端的 `InstanceManager.refresh_instances(event_type, instances)` 会按 event_type 决定是 `ADD`/`DEL`/`SET` 哪种合并语义。

## Controller 装配视角

`InstanceAssembler`（`controller/main.py:147` 实例化）负责把 deploy_config 翻译成具体的 `Instance` 对象，再调 `instance_manager.add_instance(ins)`。它决定的关键属性包括：

- `role`：按 deploy_config 决定；
- `endpoints`：按 `npu_mem_utils`/DP/TP/PP 计算每张卡的 endpoint 数量；
- `model_name`：从 `aigw_config` 或 `deploy_config.model_config` 读取。

## Scheduler 与 role 的协作

数据面 `Scheduler` 不感知 Controller 端的 role 分配细节，它只看 `InstanceManager.get_available_instances(role)` 的返回值（`scheduler.py:195-217`）：

```python
async def get_available_instance_roles(self) -> set[PDRole]:
    roles: set[PDRole] = set()
    aliases = {"both": PDRole.ROLE_U, "hybrid": PDRole.ROLE_U}
    for instance in (await self.get_available_instances(None)).values():
        role = instance.role
        if isinstance(role, PDRole):
            roles.add(role)
            continue
        normalized = str(role).strip().lower()
        try:
            roles.add(PDRole(normalized))
        except ValueError:
            if normalized in aliases:
                roles.add(aliases[normalized])
    return roles
```

兼容字符串 `"both"`/`"hybrid"` 是为了与历史 YAML 配置对齐——它们在归一化时映射到 `ROLE_U`。

## 角色与节点数的关系

`InstanceManager.get_instances_by_role(role)`（`instance_manager.py:343-351`）按 role 过滤所有非删除实例，用于：

- FaultManager 决策 ScaleP2D 时统计当前 P/D 数量；
- Observability 上报 `p_instances_num`/`d_instances_num` 给 `/v1/models`（Coordinator 端 `inference_server.py:415-423`）；
- `_report_coordinator_alarm` 检查是否有 ACTIVE 实例承担每个 role。

## 角色分配的约束

- **强分离实例的角色依然保留**：`separate_instance` 不会修改 `Instance.role`，仅切状态。运维恢复后该实例仍以原 role 重新上线。
- **不允许出现"角色冲突"**：同一 instance_id 不会同时被分配两个 role——`add_instance` 在 ID 已存在时直接返回。
- **role 与 model 强绑定**：同 role 的所有实例必须能跑同 model，否则 Conductor 查询会出现 prefix 命中假阳性。

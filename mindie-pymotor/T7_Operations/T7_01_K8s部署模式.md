# T7.1 K8s 部署模式：CRD 与多 YAML 的取舍

## 模式总览

`motor_deploy_config.deploy_mode` 决定 `deploy.py` 如何把 `user_config.json` 渲染成 Kubernetes 资源。MindIE PyMotor 当前提供三种部署方式，部署目录统一在 `examples/deployer/`，入口脚本为 `deploy.py`：

| 取值 | 含义 | 模板 | pod 创建者 | 适用场景 |
|------|------|------|------------|----------|
| `infer_service_set`（默认） | CRD 方式，输出单个 `infer_service.yaml`，含 RBAC + `InferServiceSet` | `examples/deployer/yaml_template/infer_service_template.yaml` | MindCluster infer-operator | 推荐默认；依赖 CRD，扩缩容由 `kubectl apply` 触发 |
| `multi_deployment` | 传统方式，按角色生成多份 Deployment YAML | `examples/deployer/yaml_template/{controller,coordinator,engine,kv_pool}_template.yaml` | kubectl 直接 apply | 需要 RAS 能力、KV 池化能力，或不便安装 infer-operator 的环境 |
| `single_container` | 单容器方式，P/D 合并运行 | 单容器模板 | kubectl apply | 小规模或测试场景 |

不显式配置时默认为 `infer_service_set`，对应 `docs/zh/user_guide/deployment/k8s/deploy_mode_guide.md` 中规定的语义。需要注意：**首次部署之后切换 `deploy_mode` 是不允许的**——`--update_config` 与 `--update_instance_num` 都以集群 ConfigMap 中的 baseline 为准，修改该字段会直接报错，避免部署拓扑与运行时状态不一致。

## 模式一：CRD 部署（默认）

CRD 部署通过 `mindcluster.huawei.com/v1` 的 `InferServiceSet` 自定义资源统一描述 Controller、Coordinator、Prefill、Decode（PD 分离）或 union（PD 混部）等角色。`deploy.py` 的 `generate_yaml_infer_service_set` 函数读取 `examples/deployer/yaml_template/infer_service_init.yaml`（多文档 YAML，按顺序包含 ServiceAccount `mindie-motor-controller`、ClusterRole `mindie-controller-role`、ClusterRoleBinding `mindie-controller-binding` 以及 InferServiceSet 本身），并按 `user_config.json` 做实例化。

模板填充的关键字段：

- **namespace**：取自 `motor_deploy_config.job_id`，与命名空间同名。
- **replicas**：每个 role 有两处 `replicas`——`role.replicas` 表示实例数（Controller/Coordinator 固定 1；Prefill 为 `p_instances_num`，Decode 为 `d_instances_num`；混部时 union 为 `hybrid_instances_num`，prefill/decode 置 0），`role.spec.replicas` 则对应每个 Deployment 内的 pod 数（主备时 Controller/Coordinator 为 2；Prefill 为 `single_p_instance_pod_num`）。
- **image / nodeSelector**：image 取自 `motor_deploy_config.image_name`；nodeSelector 根据 `hardware_type`（`800I_A2`、`800I_A3`、A5 派生项）由 `apply_node_selector_by_hardware`（见 `examples/deployer/lib/generator/engine.py`）写入 `accelerator-type`。
- **env**：包括 `ROLE`、`JOB_NAME`、`CONTROLLER_SERVICE`、`COORDINATOR_SERVICE` 等。Pod 启动后 CRD controller 注入 `INFER_SERVICE_INDEX`、`INSTANCE_INDEX`，`boot.sh` 据此把 `JOB_NAME` 刷新为 `{namespace}-{InferServiceSet_name}-{INFER_SERVICE_INDEX}-p/d{INSTANCE_INDEX}`。
- **RBAC**：模板中 `metadata.namespace` 与 `subjects[].namespace` 会按部署命名空间重写。

CRD 部署的优势在于：扩缩容只需修改 `user_config.json` 中的 `p_instances_num` 或 `d_instances_num`，然后执行 `python3 deploy.py --update_instance_num`，脚本会重新生成 `infer_service.yaml` 并 `kubectl apply`，由 MindCluster 的 infer-operator 完成 pod 增减，无需手动维护多个 Deployment 文件。详见 [T7.6 弹性伸缩配置](T7_06_弹性伸缩配置.md)。

## 模式二：multi_deployment 多 YAML 部署

当环境无法安装 MindCluster infer-operator，或需要 RAS / KV 池化能力时，可在 `user_config.json` 中显式配置 `"deploy_mode": "multi_deployment"`。该模式下 `deploy.py` 调用 `examples/deployer/lib/generator/` 下的四个生成器：

- `controller.py`：`generate_yaml_controller` 读取 `controller_template.yaml`，写入 `ENV_ROLE=controller`、`<job_id>-controller-<uuid>` 形式的 job 标签，并在 `motor_controller_config.standby_config.enable_master_standby=true` 时把 Deployment `replicas` 置为 2。
- `coordinator.py`：`generate_yaml_coordinator` 类似地生成 Coordinator YAML；如果 `motor_engine_prefill_config.engine_config.disaggregation_bootstrap_port` 存在，还会注入 `DISAGGREGATION_BOOTSTRAP_PORT` 环境变量。
- `engine.py`：`generate_yaml_engine` 按 `obtain_engine_instance_total` 计算 P/D（或 union）的实例总数，逐个调用 `modify_engine_yaml` 渲染。`modify_engine_yaml` 写入 image、`set_engine_env` 注入 `ROLE`/`JOB_NAME`/KVP/Ascend MF Store 等环境变量、`set_engine_replicas` 设置单实例 Pod 数、`set_engine_npu` 根据 `hardware_type` 选择 `huawei.com/ascend-910-npu` 或 `ascend-950-npu` 资源键、`apply_a5_engine_pod_config` 在 A5 机型下启用 hostNetwork 与 A5 hostPath 卷。
- kv_pool（如启用）：独立的 Deployment + Service。

最终 `output_yamls/` 目录中会出现 `controller.yaml`、`coordinator.yaml`、`engine_p0.yaml` … `engine_dN.yaml`、`kv_pool.yaml` 等文件，由 `kubectl apply -f` 逐个提交。这种方式的优势是角色边界清晰、易于手动管理，缺点是扩缩容时脚本需要对新增或删除的 engine YAML 做 apply/delete 操作，文件数随 P/D 实例数线性增长。

## deploy.py 使用方法

`examples/deployer/README.md` 列出了常用入口。最关键的三种调用方式：

```bash
# 方式一：指定配置目录（推荐），目录下需同时包含 user_config.json 与 env.json
cd examples/deployer
python3 deploy.py --config_dir ../infer_engines/vllm

# 方式二：单独指定 user_config 与 env 文件
python3 deploy.py --user_config_path ../infer_engines/vllm/user_config.json \
                  --env_config_path   ../infer_engines/vllm/env.json

# 方式三：仅刷新 ConfigMap（白名单内字段）或扩缩容
python3 deploy.py --config_dir ../infer_engines/vllm --update_config
python3 deploy.py --config_dir ../infer_engines/vllm --update_instance_num
```

`deploy.py` 依次完成：读取两份配置 → 渲染模板到 `output_yamls/` → 把 `env.json` 中的 `motor_*_env` 写入 `startup/boot.sh` 的对应函数 → 创建或更新 `motor-config` ConfigMap → `kubectl apply`。需要扩展功能（PD 混部、虚推健康探测、KV 亲和）时请参考 [T7.2 CRD 部署详解](T7_02_CRD部署.md) 与 [T7.3 Docker 多容器与 HCCL/Mooncake](T7_03_Docker多容器.md)。

## 选型建议

- **首次部署**：默认走 `infer_service_set`。需要 RAS 或 KV 池化时切到 `multi_deployment`。
- **测试环境**：若不想安装 infer-operator，可临时使用 `multi_deployment`。
- **模式切换**：必须先执行 `bash delete.sh <namespace>`，修改 `deploy_mode` 后再全量 `python3 deploy.py`，不能依赖 `--update_config` 在已有集群上做模式切换。
- **小规模验证**：可考虑 `single_container`，但生产场景不建议。

更多内容可参考 [T7.5 常见故障排查](T7_05_常见故障排查.md) 中关于部署失败时的退避步骤，以及 [T6 基础设施层说明](T6_Infrastructure/T6_02_启动脚本与HCCL工具.md) 对 `boot.sh`、`hccl_tools.py` 的拆解。

## 关键脚本路径索引

以下为 deploy.py 及各生成器的核心函数位置，便于深入追踪渲染逻辑：

| 脚本 | 关键函数 | 职责 |
|------|---------|------|
| `examples/deployer/deploy.py` | `generate_yaml_infer_service_set` | CRD 模式入口，读取 infer_service_init.yaml 模板 |
| `examples/deployer/deploy.py` | `generate_yaml_multi_deployment` | multi_deployment 模式入口 |
| `examples/deployer/deploy.py` | `create_motor_config_configmap` | 把配置写入 K8s ConfigMap |
| `examples/deployer/deploy.py` | `validate_only_instance_changed` | 扩缩容时的配置校验 |
| `examples/deployer/lib/generator/controller.py` | `generate_yaml_controller` | 渲染 controller_template.yaml |
| `examples/deployer/lib/generator/coordinator.py` | `generate_yaml_coordinator` | 渲染 coordinator_template.yaml |
| `examples/deployer/lib/generator/engine.py` | `generate_yaml_engine` | PD/union 实例 YAML 生成 |
| `examples/deployer/lib/generator/engine.py` | `apply_node_selector_by_hardware` | 根据 hardware_type 选择节点选择器 |
| `examples/deployer/lib/generator/engine.py` | `apply_a5_engine_pod_config` | A5 机型特殊配置（hostNetwork 等） |
| `examples/deployer/startup/mooncake_config.py` | `configure_mooncake` | Mooncake HCCL 通信配置生成 |

在 PD 分离场景下，engine YAML 生成器会按 `obtain_engine_instance_total` 计算 P/D 实例总数，然后逐个渲染 `engine_pX.yaml` / `engine_dX.yaml`，保证每个实例的 `JOB_NAME` 和 `ROLE` 环境变量与 Controller/Coordinator 的注册信息严格对应。

`deploy.py` 的主循环（`deploy.py` 中 `if __name__ == "__main__"` 块）依次调用配置读取、模板渲染、ConfigMap 创建、kubectl apply 四步，每一步失败都会打印具体错误并以非零码退出，便于在 CI/CD 流水线中捕获。

# T7_05_1 日志速查定位表

本文档供运维人员在收到告警或现场故障时快速定位根因。每场景包含：最小信息集（从哪拿到关键标识）、判定逻辑（搜到什么说明什么）、交叉场景区分（如何判断不是其他问题）、回退路径（搜不到或搜到矛盾结果时的处理）。

所有命令中的 `LOG_DIR` 需替换为实际日志路径。

---

## 使用入口与阅读顺序

本文档按两个入口组织：

- **入口 A（告警驱动）**：从 Grafana/CCAE 告警进入。先读「告警字段 → 最小信息集」段落，确认告警携带的字段值，再执行诊断命令。
- **入口 B（现场驱动）**：从用户投诉或命令行异常进入。先读「问题定义 + 判定条件」，确认属于哪个场景，再执行诊断命令。

不要按文档顺序阅读——按实际遇到的告警或现象直接定位场景。

---

## 通用标识符获取方法

以下标识符在多个场景中通用，先说明如何获取：

### instance_id

从告警或日志中获取。

- **Grafana/CCAE 告警**：告警的 `labels.instance_id` 或 `labels.ins_id` 字段。
- **etcd 直接查**：`etcdctl get /instances/ --prefix 2>/dev/null` 后在输出中搜索实例的 job_name 或 pod IP 对应的记录。
- **Coordinator 日志**：搜索 `instance_id=` 后跟的数字。
- **Controller 日志**：搜索 `InsStatus` 行中的数值。

### trace_id / req_id

用于串联同一次请求的全链路日志。

- **从 Coordinator 日志获取**：搜索该请求的 `model` 或 `messages` 内容特征（prompt 前几个字），定位日志行，行中的 `trace_id=` 字段即为所求。
- **从客户端**：让客户端在请求头中带上 `X-Trace-ID`，Coordinator 会透传到各 hop 日志。
- **无 trace_id 时**：用 `req_id`（格式为 `{timestamp}{counter}{uuid}`）替代，搜索范围更广但可能命中多次。

### 故障类型（FautType / AlarmType）

- **从告警名推断**：`ScaleP2DEvent` / `PrecisionIssueAlarm` / `ClusterConnectionAlarm` 等，对应文档中场景 3/6/7。
- **从日志推断**：搜索 `add_alarm` 所在行，上级日志会说明触发原因。

## 场景 1：客户端收到 HTTP 503

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`CoordinatorHigh503Rate`
- **最小信息集**：`告警携带 instance_id`，替换到以下命令
- **判定条件**：503 由 Coordinator 返回，且错误信息包含 `No routable` 或 `No compatible`

### 入口 B（命令行驱动）

- **典型现象**：客户端返回 503，Coordinator 日志有 `HTTP 503`
- **判定条件**：确认不是网关层（nginx/loadbalancer）的 503，而是 Coordinator 自身返回的

### 判定：这是场景 1 还是场景 5（NodeManager 自杀）？

两者都可能出现 503，但方向不同：

| 特征 | 场景 1（路由失败） | 场景 5（NodeManager 自杀） |
|------|---------------------|----------------------|
| Coordinator 日志 | 有 `No routable` 或 `No compatible` | 无，仅有 Controller 重启相关日志 |
| Controller 日志 | 503 是 Coordinator 侧 instance 状态问题 | 有 `reregistering` 或 `Received 503` |
| 持续性 | 持续 503 直到实例恢复 | 短暂 503 后 NodeManager 重启，自愈 |

**交叉验证命令**：

```bash
# 场景 1 特有：Coordinator 侧 503
grep -rn "No routable\|No compatible" ${LOG_DIR}/coordinator.log | tail -5

# 场景 5 特有：Controller 重启导致 NodeManager 重注册
grep -rn "reregistering\|Received 503" ${LOG_DIR}/nodemanager.log | tail -5
```

两者都搜到 → 说明场景 5 是场景 1 的次生问题，应先处理场景 1（实例状态），NodeManager 重注册会自愈。

### 步骤 1：Coordinator 侧实例视图

```bash
# 判定：是 Coordinator 视图为空，还是实例状态不对
grep -rn "available_instance_roles\|get_available_instance_roles" ${LOG_DIR}/coordinator.log | tail -10
```

- **搜到结果**（有 P/D/union 角色）→ Coordinator 视图非空，跳步骤 2。
- **无结果或只有部分角色** → Coordinator 未收到实例视图，跳步骤 3。

### 步骤 2：实例状态是否 ACTIVE（InsStatus）

```bash
# 替换 INSTANCE_ID
grep -rn "InsStatus" ${LOG_DIR}/controller.log | grep "INSTANCE_ID" | tail -10
```

- **InsStatus = ACTIVE** → 继续查路由条件，跳步骤 2a。
- **InsStatus = INACTIVE / INITIAL** → 实例未就绪，跳步骤 3。
- **InsStatus = DELETED** → 实例已删除，查删除原因。

### 步骤 2a：503 的具体原因

```bash
grep -rn "No routable inference topology\|No compatible P/D dispatch capability" ${LOG_DIR}/coordinator.log | tail -10
```

| 日志内容 | 含义 | 下一步 |
|---------|------|--------|
| `No routable inference topology is currently available` | Coordinator 侧无实例或 EventPusher 未同步 | 跳步骤 3 查 Controller |
| `No compatible P/D dispatch capability is currently available` | P/D 都在但 KV Connector 不匹配 | 引擎 kv_connector 配置不一致，查引擎配置 |
| `falling back to PDHybridRouter` | 降级到混合模式（预期内行为） | 如果需要 PD 分离，这是配置问题 |
| `PD separate service degraded to hybrid: only prefill instances available` | Decode 实例离线 | 查 Decode 实例状态 |

### 步骤 3：Controller 侧实例状态（权威来源）

```bash
# 替换 INSTANCE_ID
grep "INSTANCE_ID" ${LOG_DIR}/controller.log | grep "InsStatus\|instance_id" | tail -10

# 强制隔离判断
grep -rn "force_separated\|forced_separated" ${LOG_DIR}/controller.log | tail -10
```

- **forced_separated 非空** → 实例被强制隔离。恢复方法分两步：① `etcdctl del /controller/forced_separated/<INSTANCE_ID>` 从隔离列表移除；② 触发实例重新注册（重启 NodeManager 或手动调用 `/instances/refresh`）。仅重启 Controller 不够（`forced_separated_instances` 是内存 set，不持久化，重启后为空，但实例若已处于 INACTIVE 仍需重新注册才能激活）。
- **InsStatus = INACTIVE** → 心跳超时或实例未完成启动，跳步骤 4 查心跳。
- **etcd 中也无此 instance** → Controller 未写入，查 Controller 是否崩溃重启。

### 步骤 4：etcd 最权威状态

```bash
# 查看 etcd 中所有实例
etcdctl get /instances/ --prefix 2>/dev/null | head -50

# 查看主备锁
etcdctl get /locks/master_controller 2>/dev/null
```

- **etcd 有，Controller 日志无** → Controller 与 etcd 同步问题。若实例同时在 `forced_separated` 列表中（步骤3已有），需先执行 `etcdctl del /controller/forced_separated/<INSTANCE_ID>` 再重启 Controller；否则直接重启 Controller 即可。
- **etcd 无** → 最可能原因：实例被删除了，或者 Controller 重启后状态丢失。

## 场景 2：请求超时（504）

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`InferenceLatencyHigh` / `FirstTokenTimeout`
- **最小信息集**：`trace_id`（必需）和 `instance_id`（用于查实例状态）

### 入口 B（命令行驱动）

- **典型现象**：客户端等待时间长，最终收到 504 或流式响应中断
- **判定条件**：超时发生在 Prefill（首 token）还是 Decode（生成中途）

### 判定：Prefill 超时 vs Decode 超时

```bash
grep -rn "first_token_timeout\|timeout.*prefill" ${LOG_DIR}/coordinator.log | tail -10
grep -rn "infer_timeout\|timeout.*decode" ${LOG_DIR}/coordinator.log | tail -10
```

两者都搜到 → Prefill 超时是入口，先处理 Prefill（Prefill 是链路前端）。

### Prefill 超时判定：请求到了 P 实例吗？

```bash
# 有 trace_id
grep "TRACE_ID" ${LOG_DIR}/engine_server_p0.log | grep "dispatch\|/v1/chat\|/v1/completions" | tail -5

# 无 trace_id，用 instance_id 查
grep "INSTANCE_ID\|PREFILL_INSTANCE_ID" ${LOG_DIR}/engine_server_p0.log | tail -10
```

- **引擎侧有请求记录** → P 实例收到了请求但处理慢，查 GPU 利用率和引擎日志（OOM/CUDA 错误/算子慢）。
- **引擎侧无请求记录** → 请求未到达 P 实例，说明调度或网络有问题。

### Prefill 超时：请求未到达 P 实例

```bash
# Coordinator 侧看请求是成功发出去还是路由阶段就卡住了
grep "TRACE_ID" ${LOG_DIR}/coordinator.log | grep "dispatch\|select_and_allocate" | tail -5
```

- **有调度日志** → Scheduler 分配了实例，问题在网络/实例本身。
- **无调度日志** → 请求在 Router 入口就卡住了，查 Router 日志。

### Decode 超时判定：workload 是否过高？

```bash
grep -rn "active_kv_cache\|workload.*high\|instance.*load" ${LOG_DIR}/coordinator.log | tail -10
```

- **workload 持续高** → D 实例过载，扩缩容或限流。
- **workload 正常** → 问题在引擎侧，继续步骤 2b。

### 步骤 2b：Decode 超时——引擎侧根因定位

Decode 超时的根因分三类，均在引擎日志中体现：

```bash
# 第一类：引擎推理超时（通用）
grep -rn "Request timeout after\|Upstream inference transport failed\|All retries failed" ${LOG_DIR}/coordinator.log | tail -10

# 第二类：引擎内部错误（查引擎日志）
# max_tokens 截断（正常完成，非故障）：对比请求 max_tokens 与实际生成 token 数是否接近
# 精确字符串因引擎而异（SGLang/vLLM 格式不同），建议在引擎日志中搜 "finish_reason" 或 "stop_reason" 字段

# KV cache 满（Decode 无法写入）
grep -rn "kv.*cache.*full\|cache.*capacity\|kv.*pool.*exhaust\|CAPACITY\|capacity.*exceed" ${LOG_DIR}/engine_server_d*.log | tail -10

# 引擎内部推理错误
grep -rn "CUDA.*error\|NPU.*error\|Xid\|hccl.*error\|runtime.*error\|推理.*错误" ${LOG_DIR}/engine_server_d*.log | tail -10
```

| 日志内容 | 含义 | 下一步 |
|---------|------|--------|
| `Request timeout after XXs` | Coordinator 侧请求超时（上游引擎未响应） | 确认网络连通性到 D 实例 |
| `Upstream inference transport failed` | 引擎进程无响应或崩溃 | 查引擎进程是否存活 |
| 实际生成 token 数 ≈ 请求 max_tokens | 正常截断，非故障 | 调大 max_tokens 或优化 prompt |
| `kv.*cache.*full\|cache.*capacity` | KV cache 满，Decode 无法写入 | 扩 D 实例或清理 KV pool |
| `CUDA.*error\|NPU.*error` | GPU/NPU 硬件错误 | 查 K8s 节点事件，硬件故障 |
| 引擎日志无明显错误 | 引擎处理慢（算子/内存） | 查引擎进程的 GPU 利用率和算子耗时 |

## 场景 3：ScaleP2D 恢复后 P 实例被误停

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`ScaleP2DEvent` 或手动检查发现 P 实例数减少
- **最小信息集**：`D_INSTANCE_ID`（从告警的 `d_instance_id` 获取）、`killed_p_instance_ids`（从告警的 `killed_p_instance_ids` 获取）

### 入口 B（命令行驱动）

- **典型现象**：Grafana 发现 Prefill 实例数下降，但 D 实例数未增加
- **判定条件**：ScaleP2D 恢复流程是否在执行

### 判定：这是 ScaleP2D 恢复还是其他原因导致的 P 实例减少？

ScaleP2D 特有信号是 Controller 日志中有 `ScaleP2D strategy started`。

```bash
grep -rn "ScaleP2D strategy started" ${LOG_DIR}/controller.log | tail -10
```

- **搜到** → ScaleP2D 流程在执行，继续步骤 1 查结果。
- **搜不到** → P 实例减少不是 ScaleP2D 触发的，可能是节点故障或手动了 kubectl delete。

### 步骤 1：ScaleP2D 结果

```bash
grep -rn "ScaleP2D recovery succeeded\|ScaleP2D recovery failed\|killed_p_count" ${LOG_DIR}/controller.log | tail -10
```

| 结果 | 含义 | 处理 |
|------|------|------|
| succeeded 且 killed_p_count > 0 | 正常执行，P 被停止 | 确认 D 实例是否在等待期内恢复了，若是则参数偏短 |
| failed | 流程失败 | 查 `last_error` 字段和 `state=` 值 |
| killed_p_count = 0 | P 实例未被停止 | 说明选择逻辑未选中任何 P 实例，查选择条件 |

### 关键参数确认

```bash
# 查看实际使用的等待时间（从 ConfigMap 中取）
grep -rn "scale_p2d_d_instance_reinit_wait_timeout\|reinit_wait" ${LOG_DIR}/controller.log | tail -5
```

等待时间默认值 60s，较大模型建议 120s 以上。如果 D 实例在等待期内恢复了，下次应调大此参数。

## 场景 4：实例卡在 INITIAL

### 入口 A（告警驱动）

- **典型 Grafana 告警**：无专门告警，通常是人工巡检发现
- **最小信息集**：`INSTANCE_ID`（从实例列表中获取）

### 入口 B（命令行驱动）

- **典型现象**：`kubectl get pods` 显示实例 pod Running 但无法处理请求
- **判定条件**：实例是否真的在 INITIAL 而非 ACTIVE

### 判定：真的是 INITIAL 还是其他状态？

```bash
grep "INSTANCE_ID" ${LOG_DIR}/controller.log | grep "InsStatus" | tail -10
```

InsStatus 在各阶段的日志关键词：

| 状态 | 日志关键词 | 含义 |
|------|-----------|------|
| INITIAL | `InsStatus.INITIAL` 或初始化日志 | 实例正在初始化 |
| ACTIVE | `InsStatus.ACTIVE` | 正常运行 |
| INACTIVE | `InsStatus.INACTIVE` | 心跳超时或被隔离 |
| DELETED | `InsStatus.DELETED` | 已下线 |

### 步骤 1：NodeManager 注册请求是否发出

```bash
grep -rn "RegisterMsg\|post_register" ${LOG_DIR}/nodemanager.log | tail -10
```

- **有日志且成功** → 继续步骤 2 查 Controller 是否收到。
- **无日志** → NodeManager 未尝试注册，查 Controller 地址配置或进程是否僵死。

### 步骤 2：Controller 是否收到注册

```bash
grep "INSTANCE_ID\|register_request" ${LOG_DIR}/controller.log | tail -10
```

- **有日志** → Controller 收到了，查是否下发了 StartCmdMsg（步骤 3）。
- **无日志** → 网络隔离或 Controller 未监听，查 Controller 是否重启。

### 步骤 3：StartCmdMsg 是否正确解析

```bash
grep -rn "StartCmdMsg\|cmd.*mismatch\|para.*invalid" ${LOG_DIR}/nodemanager.log | tail -10
```

- **有 mismatch/invalid 日志** → IP/port/role 错配，检查 Controller 下发的配置与实际部署是否一致。
- **无日志但无 StartCmdMsg** → Controller 未下发，查 Controller 实例分配逻辑。

### 步骤 4：EngineServer 启动是否成功

```bash
grep -rn "pull_engine\|engine.*start\|engine.*failed" ${LOG_DIR}/nodemanager.log | tail -10
```

- **启动失败** → 引擎镜像/资源配额/权限问题，查 pod 事件。
- **启动成功但无后续** → 健康检查卡住，查 HealthCollector 日志。

## 场景 5：NodeManager 自杀

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`NodeManagerDown` 或 pod restart count 上升
- **最小信息集**：`NODE_NAME`（从告警的 pod name 获取）

### 入口 B（命令行驱动）

- **典型现象**：`kubectl get pods` 发现 NodeManager pod 在 Restart Count 增加
- **判定条件**：这是 ScaleP2D 触发的预期行为还是真实故障？

### 判定：自杀是预期行为还是异常？

```bash
# ScaleP2D 特有信号：NodeManager 收到停止 P 实例的指令
grep -rn "stop.*prefill\|stop_p_instance" ${LOG_DIR}/nodemanager.log | tail -5

# 自杀特有信号：EngineServer 进程消失
grep -rn "Engine process.*no longer running\|engine.*exit" ${LOG_DIR}/nodemanager.log | tail -10
```

- **有 stop prefill 日志但无 Engine 消失** → NodeManager 自杀是 ScaleP2D 流程的一部分，预期行为，等待恢复即可。
- **有 Engine 消失日志** → EngineServer 真实崩溃，非预期，跳步骤 1。

### 步骤 1：EngineServer 崩溃根因

```bash
grep -rn "CUDA.*error\|GPU.*fault\|OOM\|Xid\|npu.*error" ${LOG_DIR}/engine_server.log | tail -10
```

- **有 GPU 错误** → 硬件故障导致 EngineServer 崩溃，这是根因，查 K8s 节点事件。
- **无 GPU 错误** → 引擎本身异常（OOM、资源耗尽），查引擎日志。

## 场景 6：推理精度异常（NaN）

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`PrecisionIssueAlarm`
- **最小信息集**：`instance_id`（从告警的 `instance_id` 获取）、`pd_pair`

### 入口 B（命令行驱动）

- **典型现象**：推理结果中含 NaN 或 Infinity，或监控发现 token 级精度问题
- **判定条件**：精度采样检测到连续异常

### 判定：真的是精度异常还是其他推理错误？

```bash
# PrecisionReporter 触发信号
grep -rn "PrecisionReporter: threshold reached\|precision.*threshold.*hit" ${LOG_DIR}/coordinator.log | tail -10
```

- **搜到** → 精度采样已触发，继续步骤 1。
- **搜不到** → 精度问题在别处，或告警误报。

### 步骤 1：确认触发精度异常的 P/D 实例对

```bash
grep -rn "PrecisionReporter: threshold reached\|PrecisionReporter: action failed" ${LOG_DIR}/coordinator.log | tail -10
```

- **action failed** → 精度动作执行失败，查 `pd_group` 对应的实例日志
- **threshold reached** → 确认 `pd_group=(p_instance_id, d_instance_id)`，到引擎侧查具体错误

### 步骤 2：引擎侧定位精度异常根因

```bash
# 在 P 实例引擎日志中搜 NaN/Infinity
grep -rn "NaN\|nan\|Infinity\|inf\|overflow\|underflow" ${LOG_DIR}/engine_server_p*.log | tail -10

# 在 D 实例引擎日志中搜
grep -rn "NaN\|nan\|Infinity\|inf\|overflow\|underflow" ${LOG_DIR}/engine_server_d*.log | tail -10
```

- **P 实例有 NaN** → Prefill 阶段数值溢出，可能是输入数据或模型权重问题
- **D 实例有 NaN** → Decode 阶段数值溢出，可能是生成过程中的累计误差
- **仅在协调器侧有精度告警** → 可能是采样精度问题而非真实 NaN

## 场景 7：Controller 主备切换

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`ControllerDown`
- **最小信息集**：`POD_NAME`（告警中会携带 Controller pod 名称）

### 入口 B（命令行驱动）

- **典型现象**：主 Controller 故障，Standby 接管后实例状态大范围变为 INACTIVE
- **判定条件**：etcd 主备锁发生变化

### 判定：这是主备切换还是其他原因导致的实例失效？

```bash
# StandbyManager 日志：主备角色变化
grep -rn "Role changed from\|Became master, starting modules\|Failed to renew master lock" ${LOG_DIR}/controller.log | tail -10
```

| 日志内容 | 含义 |
|---------|------|
| `Became master, starting modules` | Standby 接管成为 Master |
| `Failed to renew master lock, becoming standby` | 原 Master 失去锁，降为 Standby |
| `[Standby] Role changed from` | 主备切换发生（具体方向看日志上下文） |

两者都搜不到 → 不是主备切换导致的实例失效，可能是其他原因。

### 步骤 1：确认主备切换发生的时间

```bash
# 查看 etcd 主备锁当前持有者
etcdctl get /locks/master_controller 2>/dev/null

# 对比 Controller 日志中的切换时间与实例失效时间
```

## 场景 13：L2 自愈未生效（Token Reinference）

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`TokenReinferenceFailed` 或观察到实例持续 INACTIVE 但未隔离
- **最小信息集**：`instance_id`

### 入口 B（命令行驱动）

- **典型现象**：实例被标记 L2 故障后，既不恢复也不被隔离，持续处于 INACTIVE
- **判定条件**：FaultManager 已检测到 L2 级别故障并触发策略，但实例状态未变化

### 判定：这是 L2 自愈未生效还是其他问题？

```bash
# L2 故障被检测到的信号（FaultManager update）
grep -rn "FaultManager update instance.*with event.*ABNORMAL\|strategy.*L2" ${LOG_DIR}/controller.log | tail -10
```

- **搜到 L2 策略被选中** → 继续步骤 1 查策略执行结果
- **搜不到** → L2 自愈不是问题所在，查实例 INACTIVE 的其他原因（场景 1/4）

### 步骤 1：确认 TokenReinferenceStrategy 被选中

```bash
# 查看策略选择日志（fault_manager.py:556，精确到故障代码值）
grep -rn "strategy.*code=0x00F1FEF5\|strategy.*code=0x08520003\|strategy.*TokenReinferenceStrategy.*level=L2" ${LOG_DIR}/controller.log | tail -10
```

| 日志内容 | 含义 | 下一步 |
|---------|------|--------|
| `strategy TokenReinferenceStrategy, level=L2, code=0x00F1FEF5` | Token Reinference 策略已触发 | 策略已选，等待其完成（但实际上它永不自愈，见步骤 2） |
| `strategy ScaleP2DStrategy, level=L4` | L2 故障被升级到 L4 执行 ScaleP2D | 按场景 3 处理 |
| 无策略选择日志 | L2 故障未触发策略选择 | 跳步骤 3 查故障代码 |

### 步骤 2：TokenReinferenceStrategy 执行行为分析

**重要**：当前 `TokenReinferenceStrategy.execute()` 是一个**空实现**——它只做 `while not self.event.is_set(): pass`，不会执行任何实际恢复操作。这是预期行为，不是 bug。策略会一直运行而不完成，实例保持 INACTIVE，直到被其他机制处理。

```bash
# 策略是否在运行（strategy 对象存在）
grep -rn "Instance.*strategy.*TokenReinference\|strategy_fault_level.*L2" ${LOG_DIR}/controller.log | tail -10

# 策略是否完成（strategy finished）
grep -rn "Instance.*strategy.*finished.*clearing faults" ${LOG_DIR}/controller.log | tail -10
```

- **策略运行中但无 finished 日志** → 预期行为，TokenReinferenceStrategy 是空实现，实例不会自愈
- **策略 finished** → 策略已结束，实例应恢复 ACTIVE

### 步骤 3：L2 故障持久化的根因

L2 自愈未生效的本质是 TokenReinferenceStrategy 不执行实际恢复，所以实例一直 INACTIVE：

```bash
# 实例当前状态
grep "INSTANCE_ID" ${LOG_DIR}/controller.log | grep "InsStatus" | tail -10

# L2 故障代码是否仍存在（未清除）
grep -rn "fault_code.*0x00F1FEF5\|fault_code.*0x08520003" ${LOG_DIR}/controller.log | tail -10
```

- **fault_code 持续存在** → L2 故障未被清除，需人工介入或等待超时隔离
- **实例长期 INACTIVE** → 可考虑手动隔离实例（`etcdctl del /controller/forced_separated/<INSTANCE_ID>`）或重启 NodeManager 触发重新注册

```bash
# SchedulerClient 侧：ZMQ 传输层错误
grep -rn "Failed to connect scheduler transport\|Scheduler transport not connected\|scheduler transport receive loop error" ${LOG_DIR}/coordinator.log | tail -5

# SchedulerServer 侧：无响应（超时）
grep -rn "Scheduler request timeout\|Scheduler request error" ${LOG_DIR}/coordinator.log | tail -10
```

两者都搜不到 → 问题在 Scheduler 的实例视图本身，不是 ZMQ 连接问题。

### 步骤 1：ZMQ 传输层连接状态

```bash
# 确认 SchedulerClient 连接状态
grep -rn "Scheduler transport connected\|Instance push SUB connected" ${LOG_DIR}/coordinator.log | tail -5
```

- **无连接日志** → SchedulerClient 未与 SchedulerServer 建立 ZMQ 连接，查 SchedulerServer 进程
- **有连接但报 error** → 连接曾建立但后来断裂，跳步骤 2

### 步骤 2：ZMQ 断连后的状态

**注意**：SchedulerClient 的 `_SchedulerTransport` 在 DEALER 连接断开后**不会自动重连**，也不会打印"重连中"日志。连接断开时会在 `_receive_loop` 的 exception handler 中打 `receive loop error`，此后 socket 保持 closed 状态，直到下一次 `get_available_instances` 调用才重建连接。

```bash
# DEALER 连接断连（断连时会在 _receive_loop exception handler 中打 error 日志）
grep -rn "scheduler transport receive loop error" ${LOG_DIR}/coordinator.log | tail -5

# SUB socket 推送断连
grep -rn "Instance push SUB\|recv/notify error\|recv_loop" ${LOG_DIR}/coordinator.log | tail -5
```

- **receive loop error** → SchedulerClient 无法接收 SchedulerServer 推送的消息，cache 过期后按需拉取
- **recv/notify error** → SchedulerServer 的 PUB 推送断连，SchedulerClient 降级到按需拉取（不影响调度）

### 步骤 3：SchedulerServer 进程状态（根因）

```bash
# SchedulerServer 进程存活
ps aux | grep -E "scheduler_server|scheduler" | grep -v grep

# SchedulerServer 日志（独立进程，日志路径由部署方式决定，通常为 systemd journal 或部署节点的 stdout/nohup 定向文件）
# 若使用 journald：journalctl -u mindie-scheduler-server --no-pager -n 50
grep -rn "exit\|error\|crash\|signal" /PATH/TO/SCHEDULER_SERVER.LOG 2>/dev/null | tail -10
```

- **SchedulerServer 进程不存在或已退出** → 重启 SchedulerServer
- **SchedulerServer 进程存活但 ZMQ 报错** → 查 SchedulerServer 的 ZMQ 监听端口（`ipc:///tmp/scheduler_frontend`）

### 步骤 4：IPC socket 残留导致绑定失败

```bash
# 残留 socket 文件导致新进程无法绑定
ls -la /tmp/scheduler_frontend 2>/dev/null

# 若 SchedulerServer 重启后仍无法绑定，需手动删除残留 socket
# rm /tmp/scheduler_frontend
```

## 场景 19：Controller/Coordinator OOM

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`ProcessDown` 或 Pod Restart Count 上升
- **最小信息集**：`POD_NAME`（从告警的 pod name 获取）、`NAMESPACE`

### 入口 B（命令行驱动）

- **典型现象**：`kubectl get pods` 发现 Controller/Coordinator pod 的 Restart Count 骤增
- **判定条件**：进程退出代码为 137（SIGKILL，OOM killer）

### 判定：这是 OOM 还是其他原因导致的进程退出？

```bash
# kubectl describe pod 查看退出原因
kubectl describe pod POD_NAME -n NAMESPACE | grep -A10 "Last State"

# Coordinator/Controller 进程管理器日志
grep -rn "process.*exited\|exit code\|died with exit code" ${LOG_DIR}/coordinator.log | tail -10
grep -rn "process.*exited\|exit code\|died with exit code" ${LOG_DIR}/controller.log | tail -10
```

- **exit code 137** → SIGKILL，通常为 OOM killer 触发
- **exit code 1** → 应用层崩溃，查应用日志
- **exit code 0** → 正常退出（非故障）
- **Exit code 143** → SIGTERM（信号 15），优雅退出，非 OOM

### 步骤 1：确认 OOM 的组件角色

```bash
# Scheduler 管理器日志（Scheduler 子进程退出）
grep -rn "Scheduler process exited with code" ${LOG_DIR}/coordinator.log | tail -5

# Inference Worker 子进程退出
grep -rn "Process.*died with exit code" ${LOG_DIR}/coordinator.log | tail -5
```

| 日志内容 | 含义 |
|---------|------|
| `Scheduler process exited with code` | Scheduler 子进程 OOM |
| `Process ... died with exit code` | Inference Worker 子进程 OOM |
| Controller 主进程退出 | Controller 主进程 OOM（Pod 整体重启）|

### 步骤 2：OOM 根因定位

```bash
# Pod 资源配置对比
kubectl get pod POD_NAME -n NAMESPACE -o jsonpath='{.spec.containers[0].resources}'

# Pod 内进程内存使用（若 Pod 仍在运行）
kubectl exec POD_NAME -n NAMESPACE -- cat /proc/self/status | grep -E "VmRSS|VmHWM"
```

- **VmRSS 接近 container spec 中的 memory limit** → 应用本身内存膨胀，可能是 AlarmStore 批量告警积压、实例快照缓存过大
- **memory limit 远大于实际用量但仍被 kill** → 可能是容器 cgroup 限制或宿主机内存紧张

### 步骤 3：Scheduler Server 残留 socket 清理（OOM/SIGKILL 后）

SchedulerServer 进程被 SIGKILL 杀死后，`/tmp/scheduler_frontend` socket 文件可能残留：

```bash
# 检查残留 socket
ls -la /tmp/scheduler_frontend 2>/dev/null && echo "残留 socket 存在"

# 手动清理后重启
# rm -f /tmp/scheduler_frontend && kubectl delete pod -n NAMESPACE POD_NAME
```

## 场景 20：etcd 写入失败（实例状态丢失的隐藏根因）

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`ControllerDown` 或场景 1/3/4 的告警
- **最小信息集**：无（etcd 写入失败通常作为次生问题出现）

### 入口 B（命令行驱动）

- **典型现象**：大量实例同时变为 INACTIVE，但节点本身正常；或 Controller 重启后实例列表为空
- **判定条件**：Controller 日志中出现 `Failed to persist instance assembler data to ETCD`

### 判定：这是 etcd 写入失败还是其他原因导致的实例丢失？

```bash
# Controller etcd 持久化失败信号
grep -rn "Failed to persist instance assembler data to ETCD\|Failed to restore instance" ${LOG_DIR}/controller.log | tail -10
```

- **搜到** → 继续步骤 1，确认是 etcd 写入还是读取失败
- **搜不到** → 跳回场景 1/3/4 的排查路径

### 步骤 1：区分写入失败还是读取失败

```bash
# 写入失败
grep -rn "Failed to persist instance assembler data to ETCD" ${LOG_DIR}/controller.log | tail -10

# 读取失败
grep -rn "Failed to restore instance assembler data from ETCD\|Failed to restore instance manager data from ETCD" ${LOG_DIR}/controller.log | tail -10
```

| 日志内容 | 含义 | 下一步 |
|---------|------|--------|
| `Failed to persist ... to ETCD after reregistration` | 实例重新注册后写入 etcd 失败 | etcd 连接不稳定，实例虽注册但状态未持久化 |
| `Failed to restore ... from ETCD, starting with empty state` | Controller 重启后从 etcd 恢复失败 | 查 etcd 数据完整性 |
| `Failed to persist ... after sending start command` | 下发 StartCmd 后写入 etcd 失败 | 偶发 etcd 延迟，可忽略 |

### 步骤 2：etcd 健康状态检查

```bash
# etcd 集群健康
etcdctl --endpoints=http://${ETCD_HOST}:2379 endpoint health

# etcd 磁盘空间（写入失败可能是磁盘满）
etcdctl --endpoints=http://${ETCD_HOST}:2379 endpoint status | head -5

# etcd WAL 日志大小
ls -la /var/lib/etcd/ 2>/dev/null | head -10
```

- **etcd unhealthy** → 修复 etcd 集群，Controller 会自动重连
- **磁盘满或 WAL 过大** → 清理 etcd 数据或扩容磁盘
- **etcd 正常但写入仍失败** → Controller 与 etcd 网络分区，查网络

### 步骤 3：etcd 写入失败后的实例状态恢复

etcd 写入失败期间注册的实例在 Controller 重启后会丢失：

```bash
# 确认 etcd 中实例数量（每行一个 key，2行一组）
etcdctl get /instances/ --prefix 2>/dev/null | grep "^/instances/" | wc -l

# 确认 Controller 是否在重新注册
grep -rn "RegisterMsg\|post_register\|instance.*reregister" ${LOG_DIR}/controller.log | tail -10
```

- **etcd 实例数少或为空** → 需要 NodeManager 重新注册实例（触发 NodeManager 重启）
- **etcd 实例数正常但 Coordinator 看不到** → EventPusher 同步问题，跳场景 1 步骤 1

## 场景 21：Deployer CRD 部署失败

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`ServiceDown`（组件 pod 未启动）或自定义告警
- **最小信息集**：`DEPLOYER_LOG`（Deployer 脚本输出日志路径，默认为部署宿主机的 stdout 或 `nohup` 重定向文件，如 `~/deployer.log`，具体路径由部署方式决定）

### 入口 B（命令行驱动）

- **典型现象**：`kubectl get pods` 发现组件 pod 一直是 Pending/ImagePullBackOff；Deployer 脚本报错退出
- **判定条件**：Deployer 阶段在 YAML 渲染、kubectl apply 或 Pod startup probe 失败

### 判定：这是 YAML 渲染失败还是 kubectl apply 失败？

Deployer 日志（脚本输出，非 Pod 内日志）中的典型错误：

```bash
# Deployer 脚本输出日志中搜索错误
# 注意：这是 Deployer 宿主机的日志，不是 Pod 内日志

# kubectl 不可用
grep -rn "kubectl not found\|kubectl not in PATH" DEPLOYER_LOG

# 节点选择器不匹配
grep -rn "No node in cluster matches nodeSelector\|kubectl get nodes failed" DEPLOYER_LOG

# YAML 渲染失败
grep -rn "YAML.*render\|render.*fail\|template.*error\|jinja\|jinja2" DEPLOYER_LOG

# kubectl apply 失败
grep -rn "kubectl apply\|apply.*fail\|Error from server\|error from server" DEPLOYER_LOG
```

### 步骤 1：YAML 渲染失败定位

```bash
# 查看渲染出的 YAML 是否缺失关键字段
grep -rn "MOTOR_CONTROLLER\|MOTOR_COORDINATOR\|motor_controller_config\|motor_coordinator_config" DEPLOYER_LOG | head -10

# ConfigMap 中的配置是否缺失
grep -rn "config.*not found\|missing.*config\|config.*empty" DEPLOYER_LOG
```

- **ConfigMap 字段缺失** → 检查 ConfigMap YAML 中的 `data` 字段是否完整
- **jinja2 渲染失败** → 检查 yaml_template 中的模板变量是否在参数中都有值

### 步骤 2：kubectl apply 失败定位

```bash
# 查看 kubectl apply 的具体错误
grep -rn "error from server\|Error from server\|Forbidden\|Unauthorized\|NotFound" DEPLOYER_LOG

# RBAC 权限不足
grep -rn "Forbidden\|cannot.*create\|cannot.*delete\|cannot.*patch" DEPLOYER_LOG
```

| 日志内容 | 含义 | 下一步 |
|---------|------|--------|
| `Error from server (Forbidden)` | RBAC 权限不足，ServiceAccount 缺少必要角色 | 查 K8s RBAC 配置 |
| `Error from server (NotFound)` | 依赖的 CRD/namespace 不存在 | 先创建依赖资源 |
| `Error from server (Unauthorized)` | 认证失败，检查 kubeconfig | 刷新 kubeconfig |
| `kubectl not found` | Deployer 运行环境未安装 kubectl | 在宿主机安装 kubectl |

### 步骤 3：Pod startup probe 失败定位

```bash
# 查看 pod events 中 probe 错误
kubectl describe pod POD_NAME -n NAMESPACE | grep -A5 "Events:\|Liveness\|Readiness\|Startup"

# 查看 pod 内 probe 日志（如 pod 已启动）
kubectl logs POD_NAME -n NAMESPACE | tail -20
```

- **Readiness probe 失败** → /readiness 端点返回非 200，查组件启动日志
- **Startup probe 失败** → 组件启动超时，可能是资源不足或依赖未就绪

## 场景 22：P/D 跨可用区网络隔离（KV 传输超时）

### 入口 A（告警驱动）

- **典型 Grafana 告警**：`KVTransferTimeout`（与场景 8 共用告警）
- **最小信息集**：`trace_id`（必需）

### 入口 B（命令行驱动）

- **典型现象**：Prefill 完成，Decode 等待 KV bootstrap 超时；P 实例和 D 实例不在同一 AZ
- **判定条件**：KV 传输路径跨越可用区，带宽/延迟超出阈值

### 判定：这是跨 AZ 问题还是 P/D 本身无法通信？

这是场景 8 的特例——先排除场景 8 的其他根因，再排查 AZ 隔离。

**前置：trace_id → P 实例 / D 实例 pod name 的映射**

拿到 trace_id 后，先在 Coordinator 日志中找出请求调度到了哪些实例：

```bash
# 从 trace_id 拿到 instance_id（Coordinator 日志中有调度记录）
grep "TRACE_ID" ${LOG_DIR}/coordinator.log | grep "TRACE_ID.*dispatch\|TRACE_ID.*select_and_allocate" | grep "TRACE_ID_VALUE" | head -3

# 从 instance_id 映射到 pod name（用 etcd 中实例的 job_name 或 pod IP）
etcdctl get /instances/ --prefix 2>/dev/null | grep -B5 "INSTANCE_ID"

# 或通过 pod IP 映射（ Coordinator 日志中也有 endpoint IP）
grep "instance_id=.*endpoint.*ip" ${LOG_DIR}/coordinator.log | head -10
```

拿到 P 实例和 D 实例的 pod name 后，执行 AZ 判定：

```bash
# 查看 P 实例和 D 实例的 AZ 信息
kubectl get pod P_POD_NAME -n NAMESPACE -o jsonpath='{.metadata.labels.failure-domain\.beta\.kubernetes\.io/region}'
kubectl get pod D_POD_NAME -n NAMESPACE -o jsonpath='{.metadata.labels.failure-domain\.beta\.kubernetes\.io/region}'
```

- **P/D region 不同** → 确认是跨 AZ 传输，继续步骤 1
- **P/D 同 region** → 不是 AZ 问题，跳场景 8 步骤 1 排查其他原因

### 步骤 1：跨 AZ KV 传输的确认

KV 传输跨 AZ 会体现为 metaserver 回调延迟增大或 P 实例侧 kv_transfer_params 发送慢：

```bash
# P 实例侧：KV bootstrap 发送时间（从 dispatch 到 kv_transfer_params 返回）
grep "TRACE_ID" ${LOG_DIR}/engine_server_p*.log | grep "kv_transfer_params\|bootstrap\|dispatch" | tail -5

# D 实例侧：metaserver 回调到达时间
grep "TRACE_ID" ${LOG_DIR}/engine_server_d*.log | grep "metaserver\|bootstrap\|kv_transfer" | tail -5
```

- **P 实例有 kv_transfer_params，D 实例无 metaserver 回调** → 传输在网络上丢失（跨 AZ 丢包或延迟大）
- **两者时间差 > 1s** → 跨 AZ 延迟是根因

### 步骤 2：跨 AZ 传输的处理

跨 AZ KV 传输是架构问题，无法通过日志排查解决，需要：

```bash
# 确认 P 实例和 D 实例的 AZ 标签
kubectl get nodes -L failure-domain.beta.kubernetes.io/region -L failure-domain.beta.kubernetes.io/zone

# 理想情况：P 实例和 D 实例调度到同一 AZ
# 当前解决办法：
# 1. 在 K8s 调度配置中限制 P/D 同 AZ 调度
# 2. 调整 kv_connector 的 bootstrap 超时参数
# 3. 若 P/D 必须跨 AZ，使用更大带宽的网络路径
```

- **确认跨 AZ** → 联系基础设施团队确认 AZ 间网络策略，或调整调度策略让 P/D 同 AZ
- **AZ 内传输仍慢** → 回到场景 8 步骤 2 查 KV 传输参数错误

## 文档使用小结

- **有 Grafana 告警** → 先从「入口 A」段落找最小信息集（告警携带的 instance_id 等），再执行场景内命令。
- **有命令行现场** → 先判定属于哪个场景（503/504/INITIAL/自杀等），再到对应场景按步骤执行。
- **搜到了不确定是不是根因** → 看「判定」段落（交叉信号表），确认搜到的是否与告警/现场吻合。
- **搜不到** → 说明不是该场景，检查其他场景。
- **搜到了矛盾结果** → 说明多个问题并发，以日志时间戳最接近告警时间的为先。

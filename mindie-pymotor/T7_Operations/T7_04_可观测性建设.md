# T7.4 可观测性建设：Prometheus / Grafana / Loki / Tempo

## 一键拉起栈

`examples/features/observability/stack/` 提供与 NVIDIA Dynamo 本地栈对齐的可观测性栈，涵盖 Prometheus、Grafana、Tempo、Loki、OpenTelemetry Collector 与相关 exporter。入口为 `launch.sh`，支持两种预设：

```bash
cd examples/features/observability/stack
# minimal 模式：只拉 Prometheus + Grafana + Tempo + OTel Collector
MOTOR_NAMESPACE=<namespace> ./launch.sh --minimal
# full 模式：在 minimal 基础上再叠加 Loki 与日志链路
MOTOR_NAMESPACE=<namespace> ./launch.sh
```

`docker-compose.yml` 是栈的核心。关键服务的版本与端口（受 `.env` 中的 `PROMETHEUS_VERSION`、`TEMPO_VERSION`、`LOKI_VERSION` 等控制）：

| 服务 | 镜像 | 端口（默认） | 关键启动参数 |
|------|------|--------------|----------------|
| prometheus | `prom/prometheus:v2.55.1` | 9090 | `--config.file=/etc/prometheus/prometheus.yml`、`--web.enable-lifecycle`、`--enable-feature=utf8-names` |
| grafana | `grafana/grafana` | 3000 | 预置 datasource + dashboard provisioning |
| tempo | `grafana/tempo:2.6.1` | 3200 | 读取 `tempo/tempo.yaml` |
| loki | `grafana/loki:3.3.0` | 3100 | 仅 full 模式拉起 |
| otel-collector | `otel/opentelemetry-collector-contrib:0.115.1` | 4317/4318 | 同时输出到 Tempo 与 Loki |

`--web.enable-lifecycle` 允许通过 `curl -X POST http://localhost:9090/-/reload` 热加载 scrape 配置；`--enable-feature=utf8-names` 配合 `prometheus.yml` 的 `metric_name_validation_scheme: utf8`，保留 `vllm:num_requests_running` 这类带冒号的指标名。

## Prometheus 抓取与配置发现

`prometheus/prometheus.yml` 是默认配置，`prometheus-real.yml` 是面向真实集群的发现版。栈启动后会执行一次自动发现，把 Controller/Coordinator/Engine 的 `/metrics` 端点写入 `generated/prometheus.yml`。新增抓取目标的标准做法是修改模板（`prometheus/prometheus.yml` 或 `prometheus-real.yml`）后重新 `./launch.sh`，或调用 reload API：

```bash
curl -X POST http://localhost:9090/-/reload
```

常用调试命令：

```bash
# 列出某关键字相关指标名
curl -s http://localhost:9090/api/v1/label/__name__/values | tr ',' '\n' | grep -i <keyword>

# 查询某指标当前值
curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=<metric_name>'

# 查看抓取目标状态
curl -s http://localhost:9090/api/v1/targets
```

## Grafana 数据源与看板

Grafana 账号 `motor` / `motor`（`http://localhost:3000`）。`grafana/provisioning/datasources/datasources.yml` 预置三个数据源：

| 数据源 | UID | 地址 | 用途 |
|--------|-----|------|------|
| Prometheus | `prometheus` | `http://prometheus:9090` | 指标查询（默认） |
| Tempo | `tempo` | `http://tempo:3200` | 分布式追踪 |
| Loki | `loki` | `http://loki:3100` | 日志（minimal 不含） |

栈内已配置三向联动：Tempo 的 `tracesToLogsV2` 按 `service.name` / `x_request_id` 关联日志（前后 5 分钟），`tracesToMetrics` 跳 Prometheus；Loki 的 `derivedFields` 从日志中提取 `trace_id` / `x_request_id`，一键跳到 Tempo Trace。

看板位于 `grafana/dashboards/`，由 `dashboard-providers.yml` 自动加载（无文件夹层级、`updateIntervalSeconds=30`）。当前保留三块：

- **pyMotor Metrics · 指标总览**（`motor-all-metrics.json`，UID `motor-all-metrics`）：集群概览、PD Role / Instance 分组、吞吐与延迟。
- **KV 缓存**（`motor-kv-cache.json`，UID `motor-kv-cache`）：vLLM KV Cache 使用率、prefix cache 命中率。
- **引擎性能剖析**（`motor-vllm-profiling.json`，UID `motor-vllm-profiling`）：`vllm_profiling_*` 指标族（显存、forward/execute/scheduler 时延等）。

看板顶部变量（`$cluster`、`$motor_metric_scope`、`$role`、`$pd_role`、`$dp_rank`、`$pod_ip`、`$instance_id`、`$model_name`）通过 `label_values` 查询 Prometheus 标签动态生成。新增面板时应复用这些变量并把 `allValue` 设为 `.*`，避免标签缺失导致 No Data。Grafana 容器以只读方式挂载 `grafana/dashboards/`，因此 UI 上的临时改动不会落盘，必须通过 **Edit → JSON Model → 写回源文件** 或直接编辑 JSON 文件才能持久化。`provisioner` 每 30s 自动重载，约 30 秒后刷新浏览器即可看到新面板。

## 在看板中新增面板

推荐流程：

1. **先验证 Prometheus 已抓到目标指标**（`curl -sG .../api/v1/query`）。
2. **UI 编辑**：Edit → Add Visualization → 选 Prometheus 数据源 → 写 PromQL（务必带看板变量过滤，例如 `vllm:num_requests_waiting{cluster=~"$cluster", instance_id=~"$instance_id", pd_role=~"$pd_role"}`）→ 选可视化类型（Time series / Stat / Bar gauge / Pie chart）→ Apply。
3. **写回源 JSON**：Dashboard settings → JSON Model → 复制 → 覆盖 `grafana/dashboards/motor-all-metrics.json` 或对应文件。
4. 直接编辑 JSON 时，注意 `id` 唯一、`gridPos` 控制 24 栅格布局、`datasource.uid` 固定为 `prometheus`/`tempo`/`loki`、`legendFormat` 用 `{{label}}` 渲染图例。

## Trace 与 Profiling 接入

基础指标（指标总览 / KV 缓存）无需修改 pyMotor 配置即可显示数据。Trace 与 Profiling 需要在 pyMotor 侧打开上报：

- **Tracing**：在 Coordinator 与 Engine 的 user_config 中配置 OTLP endpoint（`<obs-host>:4318/v1/traces`）。
  - Coordinator：`tracer_config.endpoint = http://<obs-host>:4318/v1/traces`。
  - Engine：`engine_config.otlp-traces-endpoint = http://<obs-host>:4318/v1/traces`。
  - `OTEL_SERVICE_NAME` 建议：`mindie-motor-coordinator`、`vllm-server-p`、`vllm-server-d`。
- **Profiling**：Engine 侧安装 `ms_service_metric`（依赖 Python >= 3.10、pyyaml、prometheus-client、posix_ipc）。启动前需要准备好 Prometheus 多进程目录：

  ```bash
  export PROMETHEUS_MULTIPROC_DIR=/dev/shm/vllm_metrics
  mkdir -p "$PROMETHEUS_MULTIPROC_DIR"
  ```

  Engine ready 后用 `ms-service-metric on` 开启采集，`off` 关闭，`restart` 重新加载配置，`status` 查看状态。之后 `vllm_profiling_*` 指标会被 Prometheus 抓取，「引擎性能剖析」看板出现数据。新增 `vllm_profiling_*` 指标后，可用 `grafana/scripts/build-profiling-dashboard.py` 重新生成剖析看板 JSON。

## 常见问题与排障

| 现象 | 处理建议 |
|------|----------|
| 看板变量下拉为空 | 对应标签未被任何指标暴露，先在 Prometheus 侧确认 |
| 新增面板 No Data | 检查 PromQL 是否带变量过滤；变量 `allValue` 是否为 `.*`；指标名是否带冒号（本栈已开 utf8 names） |
| UI 改动刷新后丢失 | 容器只读挂载，需写回 JSON 源文件 |
| Grafana 报 500/504 | 容器内 `HTTP_PROXY` 为空，避免走外网代理访问 `prometheus`/`tempo` |
| Loki 数据源不可用 | Loki 仅 full 模式启动，minimal 模式不包含 |

代理与内网拉镜像的细节（区分 Docker 拉镜像的 `HTTP_PROXY` 与二进制下载的 `PROXY_SH`）记录在 `SERVICE_GUIDE.md` 中；本文不重复展开，仅提醒在发现阶段建议关闭代理，避免误拉取公网镜像。

# 常见故障排查

## 排查思路总览

Motor 系统的故障排查可以从 Alarm 类型和 Instance 状态两条主线入手。Controller 通过 FaultManager 持续监控 PD 实例健康状态，当检测到异常时会生成对应类型的 Alarm；EventPusher 将这些事件同步给 Coordinator，Coordinator 根据事件类型决定是否停止向故障实例发送新请求。排查的第一步永远是确认具体触发了哪类 Alarm。

## 按 Alarm 类型排查

### ClusterConnectionAlarm（集群连接异常）

**表现**：Controller 无法与 etcd 或 NodeManager 建立连接。  
**可能原因**：

- etcd 服务不可达（检查 etcd 是否正常：`etcdctl endpoint health`）
- 网络分区导致 Controller 与 NodeManager 通信超时
- 证书配置错误（etcd 启用了 TLS 但 Controller 侧证书无效）

**排查步骤**：
1. 检查 Controller 日志中是否有 `ClusterConnectionAlarm` 关键字及其包含的详细信息。
2. 登录 etcd 所在节点，确认 etcd 进程状态和端口（2379/2380）监听正常。
3. 检查 Controller 与 etcd 之间的网络连通性（`telnet/ping`）。
4. 如启用了 TLS，确认两边使用的 CA 证书一致。

### InstanceExceptionAlarm（实例异常）

**表现**：某个 PD 实例上报异常，Controller 将其标记为 INACTIVE。  
**可能原因**：

- EngineServer 进程崩溃（OOM、GPU 硬件错误）
- 健康检查探针持续失败（`health_collector.py` 检测到推理引擎无响应）
- 实例内存或显存泄漏导致资源耗尽

**排查步骤**：
1. 确认实例 ID（`instance_id`）后，查询 NodeManager 日志找到对应节点。
2. 在该节点上查看 EngineServer 子进程的退出码和 core dump（如有）。
3. 检查 GPU 状态：`nvidia-smi` 查看是否有 Xid 错误（GPU 硬件故障）。
4. 确认实例是否在 `forced_separated_instances` 集合中（详见 T3_02_1），若是则需要运维手动恢复。

### CoordinatorExceptionAlarm（Coordinator 异常）

**表现**：EventPusher 检测到 Coordinator 心跳超时。  
**可能原因**：

- Coordinator 进程崩溃或 OOM
- Coordinator 所在的网络路径不可达

**排查步骤**：
1. 检查 Coordinator 进程是否存活（`ps aux | grep coordinator`）。
2. 查看 Coordinator 日志中是否有异常退出记录。
3. EventPusher 的心跳检测线程（详见 T3_03）会打印详细的心跳失败原因，查看 Controller 日志。

### PrecisionIssueAlarm（推理精度异常）

**表现**：推理结果出现 NaN、Infinity 等非有限值，或精度指标偏离基准。  
**可能原因**：

- 输入数据溢出（过大或过小的数值）
- GPU 计算单元异常
- 模型权重损坏

**排查步骤**：
1. 确认触发 PrecisionIssueAlarm 的具体实例和请求 ID。
2. 查看 checker.py（`motor/coordinator/fault_tolerance/precision/checker.py`）的判断日志，确认是何种精度问题。
3. 对比同批次其他实例的推理结果，缩小是单实例问题还是全局问题。
4. 如确认是模型权重问题，需要重新拉起该实例加载正确权重。

## ScaleP2D 恢复相关故障

### ScaleP2D 触发后 P 实例被误停止

**表现**：D 实例故障后，ScaleP2D 流程意外停止了健康的 P 实例。  
**排查要点**：

- 确认 `enable_scale_p2d` 配置为 `true`（默认为 `false`）。
- 检查 `scale_p2d_d_instance_reinit_wait_timeout` 是否设置过短（默认 60 秒）。
- 确认故障 D 实例的故障级别是否达到了 L4 及以上（详见 T4_03_2）。

详见 T4_03（ScaleP2DStrategy）中的完整触发条件和恢复流程。

## 实例健康检查失败

### 实例持续处于 INITIAL 状态

**表现**：新实例注册后一直停留在 INITIAL，不转为 ACTIVE。  
**排查步骤**：
1. 确认 NodeManager 已成功拉起 EngineServer 进程。
2. 查看 `health_collector.py` 的健康检查结果。
3. 检查 `StartCmdMsg` 中的配置是否正确（端口冲突、参数错误等）。
4. 确认 HCCL 通信是否正常（PD 分离依赖 HCCL 进行 KV-Cache 传递）。

### 实例心跳超时被标记为 INACTIVE

**可能原因**：

- NodeManager 与 Controller 之间的网络延迟过高
- NodeManager 进程卡顿（负载过高、GC 暂停）
- HeartbeatManager 的心跳间隔配置过长

**排查方法**：降低 `heartbeat_interval` 配置，检查 NodeManager 所在节点的负载情况。

## 排查工具链

| 工具 | 用途 |
|------|------|
| `kubectl logs` | 查看 Controller/Coordinator/NM Pod 日志 |
| `etcdctl get` | 检查 etcd 中存储的实例状态 |
| `nvidia-smi` | 检查 GPU 状态、Xid 错误 |
| `prometheus` / `grafana` | 查看 CCAE 监控大盘 |
| Motor 内置 AlarmStore | 查看历史 Alarm 记录（`T6_06_Alarm系统`） |

## 预防性措施

- 启用 etcd 高可用（至少 3 节点），避免单点故障导致全局状态丢失。
- 合理配置 `heartbeat_interval` 和超时阈值，避免网络抖动导致的误判。
- 在测试环境中定期模拟故障（ Chaos Engineering），验证 ScaleP2D 等自愈机制的有效性。
- 生产部署前，通过 `scale_p2d_d_instance_reinit_wait_timeout` 配置足够长的 D 实例自恢复等待时间，避免在实例自恢复过程中误触发 P 实例抢占。

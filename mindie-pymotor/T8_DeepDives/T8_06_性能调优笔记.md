# T8_06 性能调优笔记

MindIE PyMotor 在生产部署中的性能主要受三类因素影响：KV Cache 亲和策略参数、调度层与引擎层的协同时序、以及异常处理（重试、超时）带来的尾延迟。本节给出三类参数的调优经验与边界条件，作为运维与性能工程师的速查笔记。所有参数都对应源码字段，便于在 `user_config.json` 中按场景调整。

## KV Cache 亲和参数

KV 亲和策略的两个子模式由 `CoordinatorConfig.scheduler_config.kv_affinity_mode`（`motor/config/coordinator.py:L135`）控制：

- `KV_AFFINITY_MODE_UNIFIED = "unified"`：单分数融合亲和与负载。score = `prefill_load_scale × prefill_cost + load_weight × load_cost`，lower wins。
- `KV_AFFINITY_MODE_LOAD_GATED = "load_gated"`：先按负载挑前 N 个，再按 prefix 长度排序。

### `kv_affinity_load_weight`（默认 1.0）

`motor/config/coordinator.py:L138-L139`：

```
kv_affinity_load_weight: float = 1.0
```

`unified` 模式下负载项的权重。调优方向：

- **设为 0**：纯 prefix 亲和（最长 prefix 必胜）。高并发短请求场景下会让请求全部命中同一热点 endpoint，反而恶化尾延迟——一般只在调试 prefix cache 命中率时设为 0。
- **设为 1.0（默认）**：亲和与负载对等打分会避免热点；负载极不均衡时可以上调到 2~3 让负载项主导。
- **设为 0.1~0.3**：在长 prefix 命中率明显但又希望保留一定负载均衡时使用。

经验上，TTFT 优先场景下 0.3~1.0；吞吐优先场景下 1.0~2.0；负载极不均衡时可升到 3.0+。

### `kv_affinity_overlap_credit`（默认 1.0）

`motor/config/coordinator.py:L140-L141`：

```
kv_affinity_overlap_credit: float = 1.0
```

cached prefix 能抵扣的 prefill 算力比例。`prefill_cost = max(0, isl - overlap_credit × matched_tokens)`：

- **设为 1.0**：cached prefix 完全抵消对应 token 的 prefill 工作（理想模型）。
- **设为 0.5**：cached prefix 只抵消一半——保守估计，反映「prefix cache 命中后 attention 计算仍有部分 cost」的物理事实。
- **设为 0**：完全忽略 prefix 价值——等价于关闭亲和，仅按负载选。

prefix cache 命中率高（multi-turn chat 场景）时建议保持 1.0；命中策略不准确或 prefix cache 命中但 KV 被驱逐概率高时建议降到 0.7~0.9，避免乐观估计导致路由到「以为命中但实际 miss」的 endpoint。

### `kv_affinity_prefill_load_scale`（默认 1.0）

`motor/config/coordinator.py:L142-L143`：

```
kv_affinity_prefill_load_scale: float = 1.0
```

prefill_cost 项的权重。`unified` 模式下 score = `prefill_load_scale × prefill_cost + load_weight × load_cost`。`prefill_cost` 是 token 维度（prompt 长度 - 抵扣），`load_cost` 是 SHM 上报的工作负载 score（也是 token 维度）。调整这个参数控制「长 prompt 的 endpoint 选择压力」：

- 长 prompt 场景（few-shot / 长文档 RAG）：可上调到 2~3，让长 prompt 优先选空闲 endpoint。
- 短 prompt 高并发场景：保持 1.0 或下调到 0.5，避免长 prompt endpoint 选择时过度惩罚。

### `kv_affinity_load_gate_topn`（默认 0）

`motor/config/coordinator.py:L145-L146`：

```
kv_affinity_load_gate_topn: int = 0
```

`load_gated` 模式下保留的「最少负载 endpoint」数量；0 退化到 2（`kv_cache_affinity.py:L37` `_DEFAULT_LOAD_GATE_TOPN = 2`）。

- **2~3**：默认推荐——让 2~3 个 endpoint 竞争 prefix 命中度，同时控制热点的扩散。
- **1**：纯负载均衡（prefix 完全不参与），仅在 prefix cache 命中率极低的场景下用。
- **≥5**：在 endpoint 数量充足且 prefix 命中率中等时扩大候选池，能压低 TTFT。

## 调度层与引擎层的协同时序

`motor/config/coordinator.py:L159-L184` 的 `ExceptionConfig` 集中管控异常处理参数。它们同时影响调度层的重试时序与跨进程超时：

### `first_token_timeout`（默认 600s）

Prefill 与流式首 token 的超时。如果 Prefill 阶段（含 KV 传输）超时，请求会被取消并触发 transport retry。

- TTFT 优先场景：调到 60~120s，避免长 prompt 卡死。
- 长 prompt 场景：保持 600s 防止误杀。

### `infer_timeout`（默认 3600s）

整次推理（Decode 完整结束）的超时。Decode 阶段 token 数大时这个值要大。

### `max_retry` / `transport_retry_limit`（默认 5）

`max_retry`（L162）是单次请求的总重试上限；`transport_retry_limit`（L173-L174）是 transport 级别的重试上限，可显式覆盖。生产环境一般保持默认 5 次；如果网络抖动频繁可以升到 7~10。

### `retry_delay`（默认 0.2s）+ 指数退避

`motor/coordinator/router/strategies/base.py:L286-L288` 与 `L361-L363` 显示实际等待时间是 `retry_delay × 2^attempt`：

```
wait_time = self.config.exception_config.retry_delay * (2**attempt)
```

第 1 次重试 0.2s，第 2 次 0.4s，第 3 次 0.8s……总退避时间 ~3s。`retry_delay` 调大能减少重试风暴（雪崩时的常见优化），但会增加单请求尾延迟。

### `reschedule_enabled`（默认 True）

开启后请求级别异常会触发 token-id 级别的 reschedule（见 `BaseRouter._process_response_error`），而不是单纯放弃。流式场景下尤其重要——客户端已收到部分 token 时不能直接放弃。详见 `motor/coordinator/router/rescheduler/rescheduler.py`。

### `upstream_error_body_max_bytes`（默认 64KB）

`motor/config/coordinator.py:L170`。引擎返回错误响应时，Coordinator 最多读取这么多字节记录到日志/trace。64KB 足够定位大多数问题；如果引擎返回堆栈很长可以调到 256KB。

## 调度策略选择

`SchedulerConfig.scheduler_type`（`motor/config/coordinator.py:L102-L114`）：

- `LOAD_BALANCE`（默认）：按 workload 选最小 endpoint。适合 prefix cache 命中率低（如：长尾独立 query）、请求量大的场景。
- `ROUND_ROBIN`：严格轮询。适合测试与负载极均衡的小规模部署；生产一般不用。
- `KV_CACHE_AFFINITY`：基于 prefix cache 命中 + 负载打分。适合 multi-turn chat、few-shot、RAG 等 prefix 复用率高的场景。

切换策略的工程含义：

- `LOAD_BALANCE` → `KV_CACHE_AFFINITY`：要求 Prefill 实例开启 `enable-prefix-caching` 并配置 `kv-events-config`（参见 `docs/zh/user_guide/features/KV_cache_affinity.md`）。否则 conductor 拿不到 prefix cache 信息，会退化为纯负载均衡。
- `KV_CACHE_AFFINITY` → `LOAD_BALANCE`：不需要调整引擎配置；但会失去 prefix cache 命中带来的 TTFT 收益。

## HCCL 与分布式通信

虽然 PyMotor 不直接管理 HCCL，但 Prefill/Decode 跨节点 KV 传输依赖底层集合通信：

- 单节点 PD 分离：KV 在 HBM 内复制，HCCL 不参与。
- 多节点 PD 分离：KV 在节点间传输时依赖底层 connector（Mooncake、Nixl 等），它们的性能受 HCCL 集合通信配置影响。

调优建议：

- 单节点 PD：把 Prefill 与 Decode 放在同一节点可以避免跨节点 KV 传输延迟。
- 多节点 PD：确保 Prefill 与 Decode 节点在 HCCL 拓扑上相邻（同一 HCCS 域），减少传输跳数。
- Mooncake Connector 的 `kv_port`（20001/20002 之类）应在两节点之间网络可达，防火墙/安全组需放行。

## 监控与瓶颈定位

调优的前提是可观测。`PrometheusMetricsConfig`（`motor/config/coordinator.py:L149-L155`）控制 Prometheus exporter：

- `reuse_time`（默认 3s）：metric 复用时间窗口。
- `pool_metrics_enable`：是否暴露 HTTP 连接池 metrics。
- `pool_metrics_endpoint`：自定义 metrics 端点。

调优瓶颈定位的标准动作：

1. 看 TTFT ms（在 trace attribute 上，参见 `T8_04_端到端Tracing链路`）。TTFT 高：
   - 调度耗时高 → 看调度 latency 日志（`Scheduling latency stage=select_and_allocate`）。
   - Prefill 耗时高 → 看 EngineServer 的 Prefill span；KV 传输慢的话检查 HCCL/Mooncake 状态。
2. 看 TPOT ms。TPOT 高：
   - Decode 端 workload 饱和 → 考虑扩 Decode 实例或缩 Prefill 触发 ScaleP2D。
   - KV 传输跟不上 Decode → 调整 Mooncake Connector 参数。
3. 看 Prometheus metric 中的 `pool_*`：HTTP 连接池复用率。复用率高说明客户端连接管理良好；低说明频繁创建销毁连接，可能成为瓶颈。
4. 看 `add_trace_event("Scheduled Resource ok")` 与 `add_trace_event("Begin Scheduled Resource")` 之间的时间——这是纯调度耗时，理想情况下 < 5ms。

## 调优清单

生产部署前建议过一遍这张表：

| 参数 | 推荐起点 | 调整方向 |
|------|----------|----------|
| `scheduler_type` | `kv_cache_affinity`（多轮）或 `load_balance`（独立 query） | 看 trace 中 prefix cache 命中率 |
| `kv_affinity_load_weight` | 1.0 | 负载极不均衡时 +0.5~2.0 |
| `kv_affinity_overlap_credit` | 1.0 | prefix 命中率可疑时降到 0.7 |
| `kv_affinity_prefill_load_scale` | 1.0 | 长 prompt 场景 +1.0~2.0 |
| `kv_affinity_load_gate_topn` | 2 | endpoint 充足时升到 3~5 |
| `first_token_timeout` | 600s | TTFT 优先场景降到 120s |
| `infer_timeout` | 3600s | 长生成场景保持 |
| `max_retry` / `transport_retry_limit` | 5 | 网络抖动频繁时升到 7~10 |
| `retry_delay` | 0.2 | 雪崩防御场景升到 0.5~1.0 |
| `reschedule_enabled` | True | 流式场景必须开 |
| `endpoint_instance_score_weight` | 0.05 | endpoint-first 调度时设为 0 |

调优是一个持续的过程——单次修改后必须观察至少一个完整的请求生命周期（30 分钟到数小时）才能判断趋势，避免在噪声中过拟合。

# T8_05 多模型并行支持

PyMotor 在多模型并行场景下有一个被多次绕过但尚未根治的「中心化配置」瓶颈：`CoordinatorConfig` 是单例的，全 Coordinator 进程只读一份配置，无法在同一个 Coordinator 实例上同时服务多种模型的差异化策略。本节从配置中心化、Instance 视图混合、Scheduler 路由粒度三个层面分析问题，并指出当前代码里相关的妥协点。

## 单 CoordinatorConfig 的中心化

`motor/config/coordinator.py:L348-L820` 的 `CoordinatorConfig` 是 Coordinator 进程启动时通过 `from_json` 加载的全局配置，所有字段共享同一份：

- `scheduler_config.scheduler_type`（L102-L114）决定全局调度策略：要么全用 `load_balance`，要么全用 `kv_cache_affinity`，无法对模型 A 用亲和、对模型 B 用负载。
- `exception_config.first_token_timeout` / `infer_timeout`（L168-L169）对所有请求生效——长上下文模型与短上下文模型可能需要不同 timeout，但当前只能取一套。
- `prefill_kv_event_config`（L332-L346）描述全局 KV 事件/Conductor 配置：单 `conductor_service`、单 `model_path`。多模型场景下不同模型的 tokenizer 不同，但 `TokenizerManager`（`motor/coordinator/scheduler/policy/kv_cache_affinity.py:L458-L577`）是 `ThreadSafeSingleton`，同一个 `model_path` 加载一个 tokenizer，无法服务多个模型的 chat template。

`TracerConfig`（L319-L329）同样中心化——所有请求共享同一个 OTLP endpoint 与采样率。

## InstanceManager 视图与 model_name 字段

`motor/common/resources/instance.py:L143-L144`：

```
job_name:   str = Field(..., description="Instance job name")
model_name: str = Field(..., description="Instance model name")
```

`model_name` 是必要的字段，每个 Instance 知道自己跑哪个模型。但 `InstanceManager.get_available_instances(role)`（`writer.py:L60-L82` 引用）返回的是「全部该 role 的实例」——不分模型。这意味着：

- Router 在 `select_and_allocate` 时拿到的是「全部 P 实例」，需要自己按 `model_name` 过滤，否则可能把 qwen 请求路由到 llama 实例。
- 当前 `BaseRouter.prepare_resource`（`motor/coordinator/router/strategies/base.py:L269-L364`）确实没有按 model 过滤——这是「同构集群」假设的产物，多模型场景下会立即暴露 bug。

## Scheduler 的路由粒度问题

`KvCacheAffinityPolicy.select_endpoint_candidates_from_list`（`motor/coordinator/scheduler/policy/kv_cache_affinity.py:L52-L144`）接受 `instances: list[Instance]` 与 `req_info`，但 `req_info` 没有 model 维度信息。这意味着：

- Conductor 查询的 prefix cache 是「按 token id」的，与模型无关——只有同模型请求才能复用 prefix cache，多模型并行下必须先按模型分桶。
- `_collect_load_candidates`（同文件 L230-L265）从 conductor 拿到的 tenant 信息也是全局的，不分模型。

也就是说，KV 亲和策略在多模型并行下要么按 model 分桶单独跑，要么错配请求。

## InstanceReadiness 与多模型

`motor/coordinator/domain/scheduling.py:L56-L89` 的 `readiness_from_instances(instances)` 把所有可用 instance 视作同构，只看 role 组合：

```
has_compatible_pd = has_compatible_dispatch_pair(prefill_instances, decode_instances)
```

`has_compatible_dispatch_pair`（在 `motor/common/resources/dispatch.py` 中定义）按 P/D 两端的 dispatch_capabilities 配对——**不验证 model 一致性**。多模型场景下可能把模型 A 的 Prefill 与模型 B 的 Decode 配在一起，引擎层才发现不兼容。

## Controller 的 EventPusher 与多模型

Controller 通过 `EventPusher` 把 instance 状态变化推给 Coordinator；`ReadOnlyInstance.__deepcopy__`（`motor/common/resources/instance.py:L539-L566`）与 `to_instance`（L577-L610）保留 `job_name` / `model_name` / `engine_type` 等字段。Coordinator 拿到这些 instance 后存到本地 `InstanceManager`，但路由层并不主动用 `model_name` 做硬约束。

## 代码中已经妥协的几个点

1. **`aigw` 模型聚合**：`motor/config/coordinator.py:L468-L481` 把 `motor_engine_prefill_config` 与 `motor_engine_decode_config` 的 `model` 聚合到 `aigw_model` 字典，但这是给 AIGW 元数据用的，不是路由用的。Coordinator 进程仍按单一模型配置启动。

2. **`prefill_kv_event_config.model_path` 单值**：`motor/config/coordinator.py:L344` `model_path: str = ""`，加载后通过 `TokenizerManager`（`motor/coordinator/scheduler/policy/kv_cache_affinity.py:L482-L489`）读出 `AutoTokenizer.from_pretrained(model_path)`。多模型场景下应该每个模型一个 tokenizer。

3. **`KV_AFFINITY_MODE_UNIFIED` 与 `KV_AFFINITY_MODE_LOAD_GATED` 仍是单选**：`motor/config/coordinator.py:L135-L146` 的 `kv_affinity_mode` 决定全局子策略；多模型并行时无法对不同模型用不同 affinity 模式。

4. **`conductor_service` 单值**：`PrefillKvEventConfig.conductor_service: str` 单字符串。多模型共享一个 conductor 实例时只能期望 conductor 内部能区分；如果不行，必须为每个模型部署独立 conductor + 独立 Coordinator（或 Coordinator 多实例）。

## 当前可行的临时方案

虽然根治需要重构，但下面这些过渡方案在源码中可见，且能在一定程度上缓解多模型并行问题：

1. **Coordinator 多实例部署**：每个模型一套 Coordinator + 自己的 controller/nodemanager/engineserver 集群。`DeployConfig`（`motor/config/coordinator.py:L308-L316`）的 `p_instances_num` / `d_instances_num` 是单 Coordinator 内实例数，不支持多 Coordinator 集群——但 K8s 层面可以平行部署多套 PyMotor，每套绑定不同模型。

2. **`readiness` 与 `target_instance_id` 显式路由**：`BaseRouter.prepare_resource`（`motor/coordinator/router/strategies/base.py:L269-L364`）支持 `target_instance_id` 约束（由 `RequestInfo.scheduling_constraint` 提供）。业务方可以在请求层面硬指定 instance id 来绕过 Scheduler 的自动选择——但这需要业务方知道每个模型对应的 instance id，本质上是把路由逻辑搬到业务侧。

3. **`engine_type` 过滤（如果未来引入）**：`Instance.engine_type`（`motor/common/resources/instance.py:L145`）已经预留——目前仅用于 EngineServer 适配，未参与路由。可以基于此字段扩展为「按 engine_type 过滤候选」的逻辑，但这是代码改动不是配置改动。

## 根治方向

要把「同构集群」扩展到「多模型并行」，至少需要以下重构：

1. **CoordinatorConfig 多实例化**：从单 dataclass 改为 `dict[model_name, CoordinatorConfig]` 或模型独立的 ConfigResolver，每个模型走自己的策略与超时。
2. **`Scheduler` 与 `RequestInfo` 绑定模型维度**：`RequestInfo.model_name` 显式字段；Scheduler 在 `select_and_allocate` 入口先按 model 过滤候选 instance。
3. **`InstanceReadiness` 改造**：把 model 一致性纳入判断——`REQUIRED_MET` 变成 `REQUIRED_MET[model_name]`，避免跨模型配对。
4. **`KvCacheAffinityPolicy` 模型桶**：每个模型一个 conductor 查询结果缓存；`TokenizerManager` 改为按 model 多例化（不再是 ThreadSafeSingleton）。
5. **`TraceConfig` 按模型差异化**：长上下文模型降低采样率减少 trace 后端压力。

这些改动会显著增加 Coordinator 进程的内部复杂度——所以当前的「单 Coordinator + 多模型通过 K8s 多实例部署」是合理的过渡方案。后续若 Coordinator 内部引入 per-model ConfigResolver，会自然支持这一演进而不破坏 API 兼容性。

多模型并行的另一个相关议题是「跨模型的 prefix cache 是否可共享」——目前设计上假设「不可共享」（因为不同模型 tokenizer 不同）。若引入支持跨模型 prefix 共享的方案，需要进一步改造 Conductor 与 KV 亲和策略。
